# Lessons

- 配置模板方案中，不能把“服务端提供渲染后的格式”含混地并入客户端渲染。必须明确服务端 `rendered_content` 是运行时权威结果还是预览/一致性校验；本项目选择后者，SDK 仍按 `pole-mustache-v1` 本地渲染，服务端预览返回参考结果、诊断和哈希。跨语言一致性必须靠严格语法 Profile 与共享测试向量保证，不能直接要求各语言复刻完整 Go template。
- 模板预览接口必须区分 API 错误与渲染诊断：鉴权、参数和系统失败使用项目统一 `apimodel.Code` 与 `info`，不能伪装成 `RenderDiagnostic` 字符串；diagnostics 只描述模板语法、Value、类型和目标格式问题。

- 设计配置模板渲染时，不能默认“发布时渲染并固化”。当 Namespace Value 本身支持按客户端标签灰度时，发布阶段不存在唯一结果；应将模板和 Value 分别版本化发布，由客户端获取与自身匹配的原子快照、本地缓存并渲染。需要进一步区分“服务端负责灰度匹配、客户端只负责渲染”和“客户端同时负责匹配与渲染”，避免把灰度规则引擎无必要地复制到所有语言 SDK。

- 发布或推送前不能只依赖构建与功能测试判断依赖安全；必须同时检查 GitHub Dependabot、`npm audit` 和 Go 漏洞扫描。对 critical/high 告警优先升级或移除依赖；没有修复版本的直接依赖不能长期接受或静默 dismiss，应删除、替换或隔离到不进入交付物的独立工具链，并在提交后复核远端告警确实关闭。

- 设计统一治理平台时不能为了能力矩阵完整，提前把 Kafka、RocketMQ、Redis、MySQL 和 Job 纳入公共运行时治理协议。RPC 有统一调用上下文和低侵入 Interceptor，消息、存储则缺少跨产品、跨语言的一致执行 seam；在没有两个真实低侵入 Adapter 证明可标准化前，核心治理保持 RPC-first，外部中间件只做资源目录、健康、指标和原生管理集成，不展示虚假的灰度、路由、镜像或 Mock。

- 讨论“消息、存储是否被 Pole 纳管”时，必须先区分两层：非侵入式资源集成（目录、拓扑、健康、指标、原生管理）与侵入式运行时治理（路由、灰度、镜像、Mock 等）。不要解释成 Pole 自身 Store 选型，也不能因控制面可复用就默认运行时治理值得建设；结论必须以标准执行 seam、侵入成本和一致性风险为依据。

- 资源列表查询“统一”不等于把所有控件挤在同一行。单条件页面默认只保留主搜索框；多条件页面应使用“主搜索框 + 已选条件 Tag + 高级筛选浮层/面板”的渐进披露，远程查询统一显式提交，本地过滤统一即时生效。日期时间范围是高频连续区间控件，必须保持独立，不放入高级条件或 Tag。

- 日期范围筛选不能只把两个原生日期时间输入和一个“快捷选择”下拉包装后命名为 `DateRangePicker`；当用户要求范围选择器时，应提供单一范围触发器，并在同一弹层内完成连续日期范围、秒级时间、快捷范围、清空和确认，保证预设 `Date` 也按接口要求格式化后再回传。

- 新增前端依赖遇到 ERESOLVE 时，不要先把 `legacy-peer-deps` 当成最终方案；应先核对冲突链能否通过兼容范围内的最小工具链升级解决。本项目的 `i18next@25` 需要 TypeScript 5，而现有 `@typescript-eslint@5.62` 支持 `<5.2`，因此应固定到 TypeScript 5.1.x，既满足依赖契约，也不扩大为 ESLint/Vite 全链升级。

- 详情页“更紧凑”不能只靠压缩 padding 和网格：当文件身份、基本信息、标签和正文仍同时展开时，视觉依然拥挤。配置文件这类多视角资源应采用渐进披露：环境版本用横向环境 Tab，文件身份和主操作固定，内容区只保留“文件内容 / 基本信息 / 发布记录 / 订阅查询”一层资源 Tab；不要再叠加“配置编辑”外层 Tab或同时摊开基本信息与正文。

- 配置文件详情的跨环境视图是资源上下文切换，不应做成与正文同等级的大卡片；单环境时尤其要压缩为紧凑上下文条。文件身份、状态和主操作应位于同一摘要头，时间、加密和标签归入紧凑元数据区，正文编辑器作为主要工作区。Monaco 不能固定使用亮色 `vs`，必须跟随全局主题，避免暗色页面出现白色内容孤岛。

- Pole 的 `namespace` 必须明确建模为运行环境，而不是泛化的租户、团队或候选分组容器。服务名是全局逻辑标识，同名服务在不同 namespace 中表示同一服务的环境实例；配置分组按名称、配置文件按“分组名 + 文件名”、治理规则按“类型 + 名称”建立同样的跨环境逻辑身份。Website/Console 文案必须直接说明这一点，不能再使用“多租户单元”或“同名候选资源”造成歧义。

- 角色领域必须区分“可管理的角色聚合”和“三个内置角色受保护子类型”：内置角色的不可变约束不能上升为禁止所有自定义角色 CRUD。动手前先写角色类型 × 操作的验收矩阵；自定义角色可维护定义、成员和权限，内置角色只能维护用户/用户组绑定，定义与资源/API 权限固定。

- 共享治理条件编辑器切换到 Fluent UI 后，不能继续沿用“无行容器的扁平 CSS Grid + 自绘分段按钮”：这种结构会让列 padding、输入宽度和操作列相互挤压，甚至导致相邻输入遮挡 Combobox 箭头。每条条件必须成为独立语义行，使用 Fluent 原生单选、按钮、Tooltip 和字段控件，并为桌面表格与窄屏字段卡分别定义布局。共享组件嵌套在子规则卡片时，响应式必须依据组件容器宽度而不是浏览器视口；否则宽屏页面中的窄容器仍会裁掉操作列。

- 治理匹配的值来源只保留“固定值”和“请求参数”；不要把运行机器的环境变量设计成治理契约或 Console 可选能力。缺少明确跨数据面需求和统一变量注入模型时，`VARIABLE` 只会把规则行为绑定到单机环境并造成不可移植、不一致的执行结果。

- “自定义 Header（兼容模式）”若原有数据模型是每个鉴权子规则的 `traffic_match_rule`，就必须在子规则中与受保护接口一起配置 Header 匹配条件；不要为了视觉收敛把它错误提升为规则级共享 Header 凭证。服务端保留旧 `CUSTOM_HEADER` 读取兼容时，Console 也不能据此继续创建该模式。

- `API.path` 虽然在 protobuf 中复用 `MatchString`，但 API 资源只需要协议、方法、路径匹配类型和路径值；不要因为共用结构就把 `value_type` 暴露成 API 编辑项。`value_type` 仅在请求参数/条件匹配中提供用户选择；API 读写适配层应剥离遗留字段并依赖协议的 `TEXT` 默认值。

- 将治理编辑器从 Drawer 提升为独立页面时，不能只复用带 `min-height` 的页面 frame；页面根、frame、body 与内容 pane 必须形成有限高度的 flex 链，并将滚动唯一归属到内容 pane。已通过页头 portal 承接操作后，必须隐藏原始 `StickyTool` 容器，否则会渲染空白固定按钮。

- 创建规则属于长流程编辑任务，应使用可深链、可返回的独立页面；不要用抽屉承载。类型选择弹窗只负责确定规则类型，点击类型后立即导航到对应创建路由，并保留服务上下文和保存/取消后的工作台回流。

- 创建向导中的类型卡片若已能唯一决定目标表单，卡片必须直接作为创建入口；不要保留“选择后再确认”的冗余按钮。卡片应使用语义化按钮并提供明确可访问名称，确保鼠标与键盘操作走同一创建分发。

- 当页面显示的资源计数与删除前置校验冲突时，先抓取真实 API JSON 与数据库状态，重点核对 proto JSON 的 snake_case 字段是否已在前端归一化；不要把后端的资源占用保护误改成级联删除。错误通知正文应保留业务码和原因，RequestId 则收纳为一键复制操作，避免 UUID 撑坏 Toast。

- 资源清单在当前页出现长列表时，必须从页面根、工作区、表格 shell 到内容区建立可收缩的 flex 高度链：页头、指标、工具栏和分页固定，只有表格内容区滚动，并用 `overscroll-behavior: contain` 防止滚动传给页面。命名空间概览不得只统计服务；配置文件数应由后端一次性按命名空间聚合，并在摘要与行级表格同时可见。

- `/observability/v1` 属于 `pole-control-plane` 内的 `console` 模块查询接口，应由 console router/handler/provider 暴露；control-plane server 侧负责自身 OTel 上报和内部 chain entry，不应把 Console 查询接口写成 core apiserver 职责。

- Grafana-like 看板里的 variables 应按 dashboard 顶部轻量变量行处理：变量名/Label 辅助识别，控件本体保持独立边界；不要把 variables 包成厚重卡片，也不要做成 `$name` 前缀输入组。

- Grafana Stat panel 的 sparkline 虽然是辅助趋势，但不能缩成装饰性短横线；卡片里的当前值和趋势图要保持可读比例，sparkline 至少占据卡片下半部分的有效宽度和高度。

- 对齐 Grafana 风格时，优先降低 panel chrome：薄边框、低圆角、平面背景、紧凑标题；Stat panel 保持单值主视觉，sparkline 作为下半区 area 背景趋势，而不是 Fluent 风格的独立卡片装饰。

- 观测数据存储和查询过滤可以使用 UTC 时间，但 Console 图表、热力图和 tooltip 的时间轴必须按浏览器本地时区从查询窗口动态生成；不要硬编码 `12:00` 这类看起来像 UTC/占位的时间标签。

- 服务监控首页是服务级总览，筛选项只保留服务信息和治理能力；接口与实例筛选属于服务详情下钻，不应放在服务级首页。

- 服务监控首页的搜索筛选区应放在数字总览和服务级表格之间；筛选服务于表格，不要放在页头和摘要指标之间打断指标概览。

- 服务监控首页应直接以服务级表格作为主要入口；不要在服务级总览表格前追加“服务流量趋势 / 治理分布”这类图表面板，服务级入口要优先支持扫描和下钻。

- 服务监控详情页的“实例详情”不展示 JVM、GC、goroutine、Tokio 等语言运行时指标；实例页只保留实例维度调用指标、系统资源和状态联动，运行时细分指标不放在治理监控详情里。

- 服务治理监控不应按 RPC / Web 协议类型拆分页面或详情页顶部切换；服务详情应以服务、接口、实例、调用方向和治理能力为主轴，协议差异最多作为接口元信息展示。

- 系统监控和服务监控应按 Grafana-like dashboard 设计：顶部提供变量筛选，主体由 Stat、Time series、Heatmap、Distribution、Table 等面板组成；不要退化成普通控制台概览卡片。系统监控至少支持类别、接口筛选，服务监控至少支持服务信息、接口、实例筛选。

- 观测菜单中“操作”这一块属于操作审计，不应命名为“操作指标”；侧栏、页面标题、文档和验证记录都应统一使用“操作审计”，避免把审计日志类数据误归类为 metrics 指标。

- “底层已经换成 Fluent UI”与“页面呈现 Fluent UI 默认外观”是两个不同验收口径；当用户通过截图质疑控件仍像旧组件库时，要同时核对 DOM 实现和视觉预期，不能只以零依赖证明视觉迁移完成。

- Console 静态入口不能通过 Gin `LoadHTMLGlob` 在启动期缓存；前端重建会替换 hash 资源文件，SPA 根路径和深链必须在请求时读取当前 `index.html`，否则会引用已不存在的资源并出现空白页。
- Tooltip 是说明层而不是交互层，内容层必须禁用指针事件；否则悬浮提示会覆盖 Popconfirm、菜单等浮层的可点击目标，使确认动作看似失效。
- Console 请求失败提示不能只显示 RequestId；对于后端已返回标准 `code/info` 的 4xx/5xx，错误消息必须同时包含业务码、`info` 和 RequestId。请求包装层不能在内部抛出已格式化错误后又被外层 `catch` 二次泛化，否则会丢失用户可操作的失败原因。
- 用户问“所有输入框是否都检查过”时，不能把已复现的两个局部输入问题说成全量覆盖；必须区分“真实浏览器已测控件类型”和“仅静态扫描覆盖控件类型”，并补跑普通 Input、Textarea、Select、TagInput、LabelInput、InputNumber 等代表性路径。
- 治理编辑器这类复杂动态表单中，即使某个 `key` 当前只用于展示，也不要拼接 protocol/method/path/destination/name 等未来可能被编辑的字段；重复策略卡、接口行、Header 行、泳道服务行应统一使用稳定 index 或稳定行 id，避免切入编辑态后连续输入丢焦。
- 可编辑列表行的 React `key` 不能包含正在编辑的字段值，例如标签键；否则每输入一个字符都会触发行重挂载，导致输入框丢焦点、只能输入首字符。类似标签、条件、Header 键值行应使用稳定行 id 或至少稳定 index。
- Fluent Combobox/Select 如果支持 `filterable` 或 `creatable`，不能把输入框 `value` 固定为选中项展示文本；必须维护独立的输入文本状态，并在键盘输入、选项选择和 blur 时分别同步，否则用户无法连续输入过滤内容。
- 服务详情页如果已经通过身份头、摘要指标和内嵌表单覆盖核心信息，不要再追加“系统信息 / 运行状态”这类重复辅助区块；用户明确认为某块“不需要”时，应删除信息架构节点和对应回归要求，而不是只隐藏或调样式。
- 全局应用 Header 如果使用 `position: sticky`，必须显式设置不透明 `--app-surface` 背景、文本色和底部分割线；不能依赖默认背景，否则页面内容滚到下面时会透出，表现成顶部透明。
- 服务这类已有资源不应同时维护“详情页展示”和“编辑抽屉”两套形态；列表操作应进入同一个详情页，详情页内部用同一字段结构切换查看/编辑。创建可以保留短流程弹窗，但已有资源编辑不要再从列表打开独立 Drawer。
- A2A/MCP 这类宽资源表格中，列定义写了 `fixed` 还不等于页面真的固定；必须确认当前 Table 封装把 `fixed: left/right` 转成 sticky 行为，并在横向滚动后验证首列身份和尾列操作仍停在可见位置。
- 控制台资源列表页的页头和查询区应复用统一布局：页头左侧业务路径/标题/说明、右侧刷新和主创建动作；列表工具栏左侧列表名和当前数量、右侧筛选控件、查询和重置。不要让命名空间、服务、配置分组、MCP/A2A、治理工作台各自用私有 `header/filterBar/Space` 拼出不同扫描路径。
- 资源列表工具栏要保持和其它资源页一致的单行结构：左侧只放列表标题和当前数量，右侧放带控件内字段标签的筛选项、查询、重置；不要为了单个页面只用 placeholder、加说明行、专用网格或专用搜索区分支，否则治理工作台这类页面会再次和配置分组等资源页的搜索布局割裂。
- 对齐配置分组这类资源页查询区时，要同时对齐控件顺序和字段数量：优先 `关键字`，再放领域筛选项和状态筛选项，最后是 `查询 / 重置`；只补 label 但把类型筛选放在关键字前，仍然不符合统一布局。
- 资源列表页的搜索工具栏还必须和表格容器在页面层级上对齐：工具栏独立放在灰色页面背景上，白色表格面板只承载 Table 和分页；不要把治理工作台这类页面的查询区包进 `listPanel` / table surface，否则即使控件顺序正确，页面 UI 结构仍然和配置分组不一致。
- 服务这类资源的查看和编辑抽屉不要维护两套视觉结构；优先复用编辑表单的分段布局，查看态右侧字段应渲染为无边框正常文本，只是不提供编辑控件，并在底部提供“编辑”按钮后原地放开同一套表单。查看态不要显示 required 红星、字数统计、命名提示或内联校验错误，不要用灰底 disabled 输入框，也不要再用单独 `serviceView` 卡片布局导致查看页和编辑页割裂。
- AI 资源详情抽屉（MCP/A2A）也要遵守资源详情统一语言：身份摘要、关键元信息、分段内容和轻量操作按钮组；不要把刷新、编辑这类操作做成占据摘要区的大卡片按钮，也不要让 MCP/A2A 各自使用一套不同的详情密度。
- 复杂资源详情不应默认使用抽屉：治理规则、MCP 工具浏览、A2A Agent Card、主体权限信息和权限策略资源详情这类多 Tab/长内容/可深链页面，应优先做成独立详情页；抽屉只保留新建、编辑、授权、删除确认等短流程。
- 用户要求恢复原状时，应优先撤回本轮整体设计语言和样式覆盖，只保留此前明确要求的功能/品牌改动；不要继续微调侧边栏或页面视觉。对企业控制台做 redesign 前要避免过度主观重做，尤其不要在用户未确认前引入全局 token、背景纹理、侧栏重构和大范围页面 module.less 改写。
- MCP 服务列表的主入口应是“查看”而不是“编辑”或“查看工具”；查看详情里必须直接呈现工具能力，并在详情抽屉内部提供“编辑 Server”入口。资源列表行操作整体也应弱化编辑语义，统一以查看进入详情，再在详情内进入修改。
- 服务列表行操作权限不能只看前端按钮逻辑；后端列表响应如果手工构造 proto 且漏掉 `id/editable/deleteable`，admin 主账号也会在页面上显示“无权限操作”。服务列表这类响应应复用领域模型 `ToSpec()` 保留身份、审计和默认操作权限，再追加实例数等聚合字段，避免 bool 零值误伤前端。
- 命名空间是独立授权资源，specification 中对应 `ResourceType.Namespaces`，后端授权校验使用命名空间名称作为资源 ID；前端命名空间列表必须直接提供授权入口，不能只藏在详情抽屉里，也不能传不存在的 `id` 字段。通用授权抽屉展示命名空间资源时应按单段资源处理，不要显示空的第二段 `资源名称: -`。
- 配置文件也是配置中心里的可授权资源；即使当前 specification/backend 没有独立 `ConfigFiles` 资源类型、后端仍把文件操作鉴权转换到所属 `ConfigGroups`，前端也必须在配置文件详情上下文提供授权入口，并在授权抽屉中明确展示命名空间、配置分组和完整配置文件名。配置文件名可能包含 `/`，资源摘要解析时不要固定只取第三段，应合并第三段之后的完整路径。
- 前端资源列表的行操作按钮必须统一使用 `components/OperationButton` / `ConfirmOperationButton`，由共享组件维护操作语义到图标、Tooltip、`aria-label` 和 `title` 的映射；不要在各页面继续自行选择 `CreditcardIcon`、`FileIcon`、`EditIcon` 等承载查看/编辑/授权/删除语义。
- 批量替换行操作图标时，不能把同文件里工具栏刷新、重置等仍在使用的 `Tooltip` import 一起删掉；ESLint/构建不一定能捕捉 JSX 全局缺失，必须用真实浏览器检查 console，并在静态脚本中覆盖“使用 `<Tooltip>` 必须导入 Tooltip”的规则。
- 配置分组只能承载分组基础信息和标签；文件格式、加密开关是配置文件级属性，不能作为配置分组“默认配置”写入 metadata。配置分组列表可以展示配置加密数，但必须从配置文件真实聚合，不能用分组 metadata 推导加密占比或加密状态筛选。
- 配置中心抽屉新增 TDesign 控件时，必须同时更新 import 和静态反回归检查；尤其是列表行点击才会挂载的编辑抽屉，不能只验证列表首屏，否则 `Switch is not defined` 这类运行时错误会在点击后把页面打空。
- 配置分组列表只展示分组级发现和管理字段；`活跃版本`、`订阅客户端` 属于配置文件详情/订阅查询视角，不要放在配置分组列表里占列。遇到设计文档列项和用户当前判断冲突时，以当前用户明确纠正为准，并更新静态反回归检查。
- 配置中心发布记录这类审计列要从后端列表/详情响应开始完整返回 `ctime/mtime/create_by/modify_by`，不能只在前端表格补列；前端展示发布时间还应使用 `createTime/ctime/modifyTime/mtime` 兜底，操作人需要先解析用户 id，再用新标签链接到 `/auth/principals/userdetail`。
- 表格行操作里的图标按钮必须有可见悬浮提示和可访问名称；`Tooltip` 不能直接包 `Popconfirm` 这类非稳定 DOM 触发组件，应使用稳定 `span` target 包住按钮/确认组件，并同时给 `Button` 补 `aria-label` 和 `title` 作为兜底。
- 配置中心灰度规则这类“客户端/流量匹配条件”应优先复用治理侧已验证的 `TrafficMatchConditionEditor` 或其适配层；不要继续用 `ClientLabelInput` 这类私有行编辑器复制参数类型、匹配类型、匹配值和增删行逻辑，否则视觉与交互会和治理平台控件割裂。
- Console 静态资源在 `npm run build:test` 或任何重写 `console/web/dist` 后，必须重新拉起 console/all-mode 并用真实浏览器验证深链页面；只验证旧浏览器会话或 `curl /` 不够。还要检查当前 `index.html` 引用的入口 JS 在 8080 下返回 200，避免浏览器缓存旧 HTML 指向已删除的 hash asset，造成页面空白和 `/assets/index.*.js` 404。
- 配置中心可用性不能只验证入口渲染或列表查询；新建配置分组这类核心链路必须用真实账号覆盖 `POST` 请求、后端响应、创建后列表可见和删除清理，尤其要验证空标签、id 类型和缓存增量同步。
- 泳道编辑器最新规范不要求保留“实时规则 SPEC”区块；审查或静态回归脚本不能继续把缺少该区块当成问题。对齐泳道 PRD 时应以当前三段组信息、泳道、版本、审计结构为准。
- 注册发现首页只承载服务清单；服务别名是具体服务的附属入口，应放在服务详情的 `服务别名` Tab 内，并按当前 `namespace/service` 过滤和创建。不要把 `别名` 做成和 `服务` 平级的注册发现顶层 Tab。
- 中文控制台页面的页头、指标条和表格标题不能混用英文展示文案；注册发现这类主路径页面应统一使用中文。指标条数值里不要嵌套会被通用 label 样式命中的 `span`，健康实例这类 `x/y` 值必须保持单行基线对齐。
- 服务详情里的子资源清单应使用详情页内嵌密度：标题说明、右侧操作、紧凑表格、收敛空态和分页安全区；不要把注册发现首页那种外层宽表格和大空态直接嵌进详情 Tab。
- 服务详情内的子 Tab 内容需要和 Tabs 内容区四周保留稳定空隙；优先用外层 margin/gap 解决贴边，不要默认给子资源清单再包一层外部卡片或 panel，除非用户明确需要承载面。
- 按服务别名这类设计交接文档落地服务详情子 Tab 时，不能只调间距；必须同步还原交接里的信息架构和交互锚点：清单头、表格内总栏、行级复制、目标服务只读抽屉、默认命名空间和提交校验。
- 按新建服务这类设计交接文档落地创建抽屉时，不能只保留字段可提交；必须同步还原分段信息架构、字段锚点、名称实时计数/内联错误、重名校验和可编辑标签行。服务标签不能退回“暂无标签”占位或只做重复 key 校验。
- 创建服务抽屉里有字段锚点 wrapper 时，字段间距必须挂在 wrapper 层而不是只依赖 TDesign FormItem 内部 margin；命名空间/名称、部门/业务这类连续输入不能贴在一起。双列标签编辑器存在时抽屉宽度不要卡在 600px，应至少按 `min(720px, 94vw)` 验收。
- 服务、命名空间、用户、策略等资源标签编辑应优先复用统一 `LabelInput` 控件；不要为单个抽屉复制一套私有标签表格。标签空态没有行级对象，操作列不能放“添加标签”，添加入口只保留在底部工具行，行内操作列只放删除。
- 注册发现服务列表应和命名空间管理保持同一工作台骨架：页头右侧放刷新/新建服务，指标条和列表是独立区块，不要用白色大卡片包住指标和表格；指标条还要和下面的列表标题/筛选/表格形成明确垂直分组，不要贴在一起。
- 注册发现这类固定工作台列表页行数变多时，滚动归属应下沉到表格内容区：页头、指标条、筛选栏和分页保持在视区内，页面外层不跟着滚。实现上必须建立 `height -> flex:1 -> min-height:0` 高度链，并验证 `.t-table__content` 的 `scrollTop` 可由滚轮改变。
- 权限策略资源信息页签是左右分栏时，应把滚动所有权下沉到左右 pane：左侧资源类别列表和右侧资源详情主区分别 `overflow: auto`，外层 Tabs、Drawer body 和页面保持不滚；不要只做一个整页签滚动层。
- 权限策略详情这类包含概要和 Tabs 的查看抽屉，应固定 Drawer body，把长内容滚动挂到 Tabs 内容区，并设置 `overscroll-behavior: contain` 阻止滚动链传到背景页面；不要让整个详情页或外层页面跟着滚。
- 权限策略详情概要区只保留识别策略所需的短信息；不要在概要卡里放策略 ID、来源、成员数量或可访问接口统计，这些会稀释主信息。成员与接口留在对应页签内。
- 治理工作台新建规则类型卡片不要再写 `新建 XXX 规则` 这类重复标题；弹窗标题和按钮已经表达新建动作，卡片内部只保留类型标签和适用场景说明。
- 治理工作台新建规则的类型选择卡片要说明适用场景，例如什么时候用路由、限流、熔断、泳道等；不要只重复“新建某规则”，否则用户无法在选择阶段判断该选哪个规则类型。
- 治理工作台筛选栏右侧操作顺序应是 `刷新 / 重置筛选 / 新建规则`；新建规则作为主动作使用文字按钮，并通过两步向导先选择规则类型再进入具体创建抽屉，不要只用一个 `+` 图标下拉直接创建。
- 注册发现服务列表的行操作要和治理工作台保持一致：主入口是单个 `查看 / 编辑`，删除独立；不要把编辑、查看或授权这类近似管理入口并列成多个图标挤在操作列。
- 治理工作台列表右侧列顺序应保持 `状态` 在 `操作时间` 前，最后才是 `操作`；不要把操作时间放在状态前，否则右侧扫描路径会显得和用户预期相反。
- 限流、路由、鉴权、镜像、Mock、泳道等治理规则只要复用共享 `TrafficMatchConditionEditor` 并展示 AND/OR 分段控件，编辑态就必须接通 `relation`、`relationEditable` 和 `onRelationChange`；不要把关系硬编码为 AND 或把分段控件做成不可交互展示态。
- 设计 pole-control-plane 观测闭环时，不要绕开现有 `history`、`discoverEvent`、`statis` chain 插件架构另起独立 `openobserver` 插件类型；应优先新增可配置的 `otel` chain entry，把内部观测模型转换为 OTel logs/events/metrics/traces 后发送到内置观测后端。
- 给 Codex/Claude 这类 agent 使用的启动脚本不能只有前台 `exec` 常驻服务模式；默认可保留终端前台语义，但必须提供 `--detach` / `tmux` 优先的后台模式，避免工具调用被长进程阻塞或结束后回收服务。
- 治理工作台筛选按钮要使用短产品名保持横向扫描一致：调用鉴权显示为 `鉴权`，流量镜像显示为 `镜像`，流量 Mock 显示为 `Mock`；不要在筛选按钮里重复“调用/流量”前缀。
- 泳道组详情抽屉下的子泳道列表不应复用普通宽表格；抽屉内子资源列表应优先做紧凑规则行，固定展示名称、状态、描述、标签、条件和右侧图标操作，并隐藏 `0001-01-01` 这类聚合子对象零值时间。
- 更新仓库级 `AGENTS.md` 时，除了协作流程和架构说明，也必须明确写出“怎么 run 程序”：本地后端启动、默认 all 模式、server-only、console-only、关键端口和 `--mode` 覆盖关系，不能只保留一条测试配置启动命令。
- 当讨论 pole-control-plane 与 pole-console 的启动/部署标准化时，默认启动语义应是合并启动；参数只用于切换单独启动 `server` 或单独启动 `console`，不要把默认设计成只启动 control-plane 后再通过 `--console` 打开控制台。
- “合并启动”在 pole-control-plane / pole-console 场景里应优先理解为代码与运行时合并进 control-plane，而不是由 control-plane 再拉起一个 pole-console 外部子进程；除非用户明确要求双进程 runner，否则不要把子进程方案当成默认实现。
- 合并 console 后，默认产品入口端口优先给 console 使用 `8080`；如果 Apollo 协议端口与 console 冲突，应调整 Apollo 端口，不要挤占 console 默认入口。
- pole-control-plane 的默认启动模式必须按 `all` 理解和演示；`server`、`console` 只作为显式参数/配置指定的单独启动模式。
- 验证 console 页面数据时，必须验证 `8080` 页面运行时实际请求链路；后端 `8090` 接口返回数据只能证明服务端有数据，不能替代页面渲染验证。
- 对用户宣称 `8080` 可访问前，不能依赖 Codex 工具前台会话或普通 shell 后台子进程作为长期运行证明；需要确认服务脱离工具会话后仍由稳定进程管理，例如本机可用 `launchctl`，并再次验证端口、首页、静态资源和真实 API。
- 修复 console 鉴权问题时，不能只验证重新登录后的 curl；还要覆盖浏览器已有 `localStorage` token / `jwt` cookie 的旧登录态。后端代理不应在后端 401 前续期旧 JWT，前端遇到 HTTP 401 或 `401001` 应清理登录态并回登录页。
- 当用户评价页面设计时，先确认具体页面、抽屉、弹窗或空态；不要只优化主列表页，二级页面和无数据状态也必须按用户截图逐项处理。
- 泳道规则编辑器一旦把 `泳道规则 / 泳道组 / 版本 / 审计` 作为自身真实信息架构，父级泳道详情就不能再包通用 `RuleTabs` 的 `规则 / 版本 / 监听`；泳道类型应直出 `LaneGroupEdtor`，避免双层 Tab。
- 治理抽屉里的专用编辑器不能在公共抽屉 padding 之内继续叠加大块卡片间距；泳道这类双栏编辑器应把 pane、section、card 的 padding/gap 控制在紧凑工作台密度，避免内容像被二次缩进。
- 对齐泳道 PRD 时不能只做泳道规则列表；默认左侧必须是 `组信息`，按 `基础信息 / 泳道组入口 / 组内服务` 三段步骤卡组织，泳道规则定义放到独立 `泳道` Tab。对照 PRD 时必须同时检查查看态和编辑态。
- 泳道规则 Tab 的单条泳道不能退回路由规则表格或普通横排输入形态；应按 PRD 展开卡片实现卡头摘要、泳道名称与标签、固定标签提示条、流量匹配分段控件、四字段匹配行、组内服务行和拓扑演示。
- 按 PRD 截图还原泳道卡片时，不能把局部控件和字体做得比治理抽屉其它编辑器更大；应统一回到 12px 标签/提示、14px 主文本、32px 常规输入控件和紧凑 section 间距，避免单个模块显得突兀。
- 治理抽屉内使用 TDesign Tabs 承载长内容时，不能只给外层 pane 加 `overflow:auto`；如果 `.t-tabs` / `.t-tabs__content` 自身 `overflow:hidden`，外层不会产生 scrollHeight。应让 tabs 为 column flex，并把滚动明确挂到 `.t-tabs__content`，同时用真实 DOM 验证 `scrollHeight > clientHeight` 且 `scrollTop` 可变化。
- 修复抽屉滚动不能只证明某个内部节点可以脚本设置 `scrollTop`；必须用用户实际滚轮命中区域验证目标滚动容器。若用户期望左侧整体滚动，优先让左侧 pane 成为唯一 scroll owner，避免 Tabs 内部滚动层和外层 pane 竞争或命中不一致。
- MCP tools 页面不应按普通后台表格处理；带有 input/output schema 的工具能力更接近 OpenAPI 文档，应优先设计为工具目录、参数/响应字段、示例和 raw schema 折叠的 API 浏览体验。
- MCP Server 注册语义应优先围绕 backend selector：关联 Pole 已注册服务时只要求 `backend_type=service` 和服务 `namespace/name`；只有自定义地址模式才要求用户提供 address，不要再把 `reference` 当成唯一后端表达。
- 排查 console 列表“接口有数据但页面为空”时，要优先核对标准响应解包：当前后端列表通常返回 `{data, amount, size}`，旧前端字段如 `services`、`namespaces` 只能作为兼容兜底，不能作为唯一数据源。
- 修复某一个列表页的响应字段错位后，必须横向扫描同目录其它列表页；不要只修用户指出的页面，同类字段如 `instances`、`users`、`userGroups`、`aliases`、`configFileGroups` 都可能同时落后于标准 `data/amount` 响应。
- 服务订阅页面展示的是服务关系，不应直接退化成三列表格；优先使用 caller -> callee 的关系流、节点和方向线表达，减少重复文字，让用户一眼看到谁订阅了当前服务。
- 服务详情、实例、订阅这类可直接访问的详情页不能依赖列表页写入的 Redux 临时态；刷新或直达页面时必须从 URL 参数恢复上下文并重新拉取数据。
- 服务详情页不能只使用裸 `Descriptions` 或单列字段分段；设计原型已经明确时，必须同步落到真实 Console 源码。页面按“服务身份头部 → 四项摘要 → 基础信息/运行状态双栏”组织，基础信息内部可用受控双列键值布局，ID 与描述跨列，窄屏再退化为单列；不要把“避免三列拉散”错误收敛成全页单列堆叠。
- 实例详情抽屉也不能使用裸 `Descriptions` 单列字段；应先展示 `host:port`、健康/隔离/健康检查等关键状态，再把运行信息、位置和标签分组，避免右侧抽屉显得像未设计的表单清单。
- 治理规则原型不能做成带大量解释性文案、PRD 入口和“为什么这样设计”的 AI 化页面；应对齐 TDesign 与现有服务/实例详情风格，默认只展示产品态信息：身份摘要、关键状态、基础信息、作用范围、规则定义、发布与订阅。
- 治理规则详情不能和当前治理规则实现差异过大；即便做抽屉或视觉优化，也应保留现有规则详情/编辑页的信息顺序：基础信息、目标服务、匹配条件、动作配置、发布记录，而不是迁移成另一套服务/实例详情信息架构。
- 治理规则详情的 demo/PRD 字段必须从真实 `github.com/pole-io/specification` proto 和现有前端 service 类型推导；不能把路由、限流、熔断、探测、无损上下线、泳道抽象成一套泛化字段后再展示，否则会和实际规则 spec 对不上。
- 治理规则详情的“对齐 spec”不能理解成在产品页直接展示 proto 字段名；spec 只用于保证数据结构和含义正确，页面呈现应优先复用当前 8080 治理规则详情/编辑页的分区、表单语言和用户可理解的字段文案。
- 治理规则列表页可以做统一工作台规范优化，但详情框应沿用当前 8080 治理页面的右侧详情面板和 `规则 / 版本 / 监听` 结构；不要把详情交互替换成新的抽屉模式，除非用户明确重新要求。
- 治理规则详情交互可以是抽屉，但抽屉内部的信息架构和视觉必须复用当前 8080 治理详情页；不要把“保持当前设计”误解为把抽屉改成常驻右侧详情面板。
- 元数据/标签编辑是跨服务、实例、命名空间、配置、认证等多处复用的核心控件，不应使用普通表格内联编辑；优先做成明确的键值编辑器，提供空态、重复 key 提示、直接新增/删除和紧凑扫描体验。
- 同一资源的查看态和编辑态必须使用同一套信息架构与分区命名；编辑态只应把只读值替换成控件，不能另起“运行配置/状态控制/元数据”等不同语言，造成同一抽屉前后风格割裂。
- 即便上游流程或 skill 模板给出英文提示，也必须转写为中文再发给用户；不要直接输出英文流程话术。
- 治理页面验证不能只看 8080 静态资源或 mock 页面；用户指出 8080 正常但接口仍报错时，必须用真实登录态或等价 JWT 走 8080 console 代理请求，并结合 runtime 日志和 MySQL schema 排查 5xx。
- 整理侧边栏时不能只验证当前模块和隐藏菜单结果；必须横向点击验证所有一级模块及其关键子菜单。TDesign Menu 的 `defaultExpanded` / `expandMutex` 组合不能在未验证点击交互时贸然改为只展开当前模块，否则可能造成隐藏子菜单仍占位并拦截点击。
- Console 侧边栏一级模块顺序应把 `AI 工具` 放在 `命名空间` 后面，再展示注册发现、治理、监控和认证；不要按普通后台末尾附加 AI 模块。
- 验证认证策略页面时必须同时覆盖自定义策略和默认策略；默认策略包含 spec 中更多系统资源类型，不能只用 `default=false` 或空列表证明策略查询正常。资源类型到 Console 响应字段的 map 下标调用前必须做存在性检查，避免新增资源类型导致 nil 函数调用。
- 用户、用户组、角色这类主体详情页的“关联策略/权限信息”不能用主体类型直接隐藏；即使是 `main/admin` 主账号，也要按 `principal_id + principal_type` 查询并展示关联策略，否则后端默认策略存在但 Console 详情页看不到。
- 注册发现列表页需要与 MCP 页面保持同一套控制台工作台风格：页头、指标栏、筛选工具栏和表格摘要列可以统一，但必须保留服务/别名 tab、服务详情跳转和原有操作链路，不要为注册发现另起一套视觉语言；网关应作为注册发现左侧菜单下的独立页面，不要合并进服务实例页内部 tab。
- 治理或注册发现讨论里的 Gateway 不能默认等同于 xDS 托管的 Envoy Gateway 运行态；用户说的 Gateway 可能是自有 nginx、APISIX、Spring Cloud Gateway、Envoy Gateway 等入口资源。设计前必须先区分“用户自有网关资源登记与关联治理规则”和“control-plane 直接生成/下发 xDS 网关配置”两条边界。
- 用户明确要求先忽略 Gateway、回到服务治理规则配置模板时，范围只放在服务到服务的治理规则生成体验：路由、限流、熔断、主动探测、无损、泳道、调用鉴权、流量镜像、流量 Mock；不要继续展开网关资源登记或网关适配器设计。
- 注册发现服务页优化不能只套 MCP 视觉骨架，还要检查实际截图里的区块间距：Tabs 内容区需要明确内边距，指标、工具栏、表格之间要有稳定 gap；表格首列不要重复展示已经有独立列的可见性信息，否则页面会显得拥挤且没有呼吸感。
- 注册发现服务列表中命名空间应作为独立表格列，不要藏在服务名副文本里；健康实例列不要用 `暂无实例` 这类副文案撑高行高，服务清单默认使用中等密度表格和较小单元格 padding。
- 治理规则清单的创建时间和更新时间应参考服务列表合并为一个操作时间列，主行展示更新时间、副行展示创建时间；不要拆成两个时间列挤占右侧空间。
- Console 侧边栏折叠态只应显示项目 logo 标记本身，不能换成其它插图或复杂图形；展开态使用完整品牌标识，折叠态使用同源 mini 标记，并保持固定尺寸居中。
- 治理规则详情抽屉既要沿用现有 `规则 / 版本 / 监听` 和编辑器分区，也要按抽屉产品形态重新处理标题区、正文留白和操作安全区；不要让 `StickyTool` 按页面级偏移漂浮到抽屉内容中间遮挡表格。
- 治理规则详情里的表单查看态不能像冻结的编辑表单；优先用 inspector 风格的弱边框分区、稳定间距和轻量表格表达规则定义，减少多层卡片阴影和 hover 浮起效果。
- 治理规则详情抽屉如果把 `StickyTool` 视觉改成标题栏按钮组，点击事件必须绑定到可见的图标+文字操作内容上，并用 8080 真实页面验证 `编辑 / 发布`；不要只改样式或只依赖 `StickyTool` 容器事件，否则文字/背景点击可能失效。
- 治理规则路由详情展示必须兼容新 spec 结构：真实数据可能在 `routing_config.caller/callee` 和 `rules[].arguments.arguments`，不能只读旧的 `rules[].sources[0].arguments`；验证时必须确认主调、被调、匹配 key/value、目标分组和实例标签都实际出现在 8080 页面。
- 治理规则详情字段修复不能只看某一类规则；路由、限流、熔断、主动探测、无损上下线、泳道都可能存在 spec JSON、DB JSON、API JSON 命名和前端读取字段不一致。修复时优先在 service 层做归一化，并用 8080 逐类打开抽屉验证关键字段是否真实展示。
- 治理规则详情抽屉的查看态不能沿用编辑态 `FormItem` 堆叠；当用户反馈对齐和滚动问题时，应优先把查看态改成紧凑 definition grid、关系摘要和固定列宽表格，编辑态再保留原控件，避免为只读展示付出表单布局的高度成本。
- 治理规则抽屉优化必须同时检查查看态和编辑态；TDesign `FormItem` 的固定 label width 与 controls margin 放进 CSS grid 后可能把内容区压到极窄，出现“暂无标签”逐字竖排。编辑态需要单独的控件友好 grid，并用真实 8080 点击 `编辑` 后验证。
- 治理规则编辑态表格不能只看表格整体是否溢出；还要检查单元格内交互控件是否互相覆盖。TDesign 横向 `InputNumber` 至少需要稳定列宽，否则会压到后续标签列；验证时要对关键控件做 DOM rect 对比，例如 `weightRight <= tagLeft`。
- 治理规则编辑器里子规则和实例分组有天然顺序语义时，不能只靠“添加/删除”维护列表；应提供折叠摘要和拖拽排序。拖拽只调整本地 `routing_config.rules` 或 `destinations` 数组，保存时再统一提交，避免拖动即触发后端写入。
- 治理规则中不同类型的多策略/子规则区块要保持一致的信息架构：路由子规则、限流子规则、熔断策略都应使用规则块 header 摘要、可折叠正文和表格化定义；不要让某一类退回 TDesign Collapse 或多层灰底卡片。
- 治理规则详情里同类规则块标题应统一为 `规则 [n]`，不要在限流等页面额外写成 `子规则 [n]`；分组标题下方避免放解释性长文案，优先把必要信息压缩到规则块 header 摘要中。
- 限流规则详情的规则块列表不需要外层 `子规则` 标题；内部 `规则 [n]` 已能承担结构识别，避免“子规则 / 规则 [1]”两层标题重复。
- 治理规则详情抽屉关闭时必须销毁或重置内部编辑器状态；用户未保存直接关闭后，重新打开同一规则应回到查看态，不能沿用上一次的 `editorState.editable=true`。
- 治理规则发布页不能沿用页面级长表单；应按抽屉产品形态展示规则身份、版本信息、发布策略和灰度条件，灰度条件用表格化条件行保证对齐，并保留原 `MatcheLabel[]` 提交结构。
- 治理规则发布页的策略选择不能只放普通 radio；发布范围应通过可点击策略卡和轻量流向图表达，全量/灰度的生效对象要一眼可见。抽屉 footer 也不能让按钮散落，应固定为当前策略摘要加右侧主次操作。
- 治理规则详情查看态必须全链路只读；不能只隐藏保存按钮，所有 `InputNumber`、`Switch`、`Textarea`、表格编辑器和弹窗入口都要受 `editorState.editable` 控制。查看态优先渲染文本、Tag 或只读代码块，编辑态再渲染输入控件。
- 治理规则查看态横向排查不能只看用户截图中的那一类规则；无损上线这类使用 `readonly/borderless/disabled` 保留 `InputNumber` 或 `Switch` 外壳的实现也会让用户觉得可改，查看态应优先渲染纯文本或 Tag，编辑态再渲染控件。
- 治理规则 MySQL 模型收敛按方案 A 理解：`governance_rule/governance_rule_release` 覆盖所有治理规则类型，包括泳道；泳道以 lane group 为聚合根，lane rule 是 group JSON 内的子对象，不再默认保留 `lane_group/lane_rule/lane_group_release` 专用表。若用户明确说不考虑数据迁移，实现方案不需要为旧分表数据做自动迁移。
- 统一治理规则表后，cache 也要统一更新源：由 `GovernanceRuleUpdateCache` 轮询统一表并按 `rule_type` fan-out 给各类型 watcher；不要让路由、限流、熔断、探测、无损、泳道 cache 各自再查一次 DB。
- 完成数据库模型收敛后，必须同步清理三类残留：SQL 初始化脚本、测试/运维清理 SQL、以及本地真实数据库中的旧表；不能只改 store 实现就认为收敛完成。真实库删表前要先确认旧表为空或明确迁移策略。
- 判断历史表名是否仍有效时，必须同时核对 SQL DDL、真实库 `information_schema`、store 实现和测试套件直接 SQL；不能因为某个历史注释或测试残留就把它误判为仍需保留的独立表。
- 长期技术方案和架构/领域知识必须归档到 `context-kg` 并遵循其 schema、index、log 规则；不要在 `docs/design` 下新增孤立方案文档。`context-kg/tasks` 仅用于计划、进度、review 和 lessons。
- 调整 `context-kg` 时不能只移动文档内容，还必须同步设计和更新知识库 taxonomy：业务知识放 `business/`，技术方案和 ADR 放 `technical/adr/`，模块/接口/环境/约定放 `technical/` 对应子目录，测试/缺陷/自动化知识放 `quality/`；同时更新 `_meta/schema.md`、`_meta/index.md`、`_meta/log.md` 和仓库级 AGENTS/CLAUDE 规则。
- 设计 pole-control-plane 的 A2A 能力时必须严格限定为 A2A Agent Registry：Agent Card 注册、发现、索引、治理元数据和管理 API。A2A task proxy、SSE streaming 转发、push notification broker、task 状态机和 artifact 存储属于数据面/网关/agent runtime，不应写成 pole-control-plane 的二期能力。
- 实现 A2A Agent Registry 时不能只落后端注册表；Console 页面、列表筛选、抽屉新建/编辑、Agent Card 查看和技能详情都属于功能完整性的一部分，需要和 MCP 页面保持同一套控制台交互语言。
- 验证 A2A Console 页面数据时必须走 `8080/ai/a2a/v1` 代理链路；`8090/ai/a2a/v1` 有数据只能证明后端和缓存正常，不能证明 Console 已注册对应反向代理。新增 AI Native API 前缀时要同步 Console router 和 router 测试。
- 新增 AI Native API 后，测试配置和本地 all 模式发布配置必须同时启用对应 apiserver 配置；不能只改 `test/data/bootstrap/pole-apiserver.yaml`，还要同步 `deploy/conf/pole-apiserver.yaml`，否则 8080 页面会因 8090 未注册路由而返回 404。
- A2A、MCP、服务列表都属于同一控制台工作台体系；新增 A2A 页面不能只做裸 toolbar + table，应复用页头、指标栏、筛选栏、表格容器、摘要单元格和详情抽屉摘要区，保证用户在 AI 工具和注册发现之间切换时布局语言一致。
- A2A Agent 列表中 Agent Card、技能和编辑不应拆成多个并列 action 图标；应保留一个 `查看 / 编辑` 入口打开统一详情抽屉，再在抽屉内部通过 Tabs 切换 Agent Card、技能和编辑视图。
- 控制台顶部筛选功能栏不要用普通 `Space` 把分段按钮、输入框和操作按钮散开；筛选项多时应放进统一工具面板，用分组标签、稳定网格和明确 action 区控制换行，否则宽屏下也会出现协议按钮孤立、查询/重置掉行的问题。
- A2A 这类筛选维度多的列表页，不应把协议筛选做成独立 chip 分组再和高级筛选并列；应把所有筛选项纳入同一个确定性 grid，并给表格关键列设置稳定宽度和表头 nowrap，避免宽屏或中等宽度下出现意外拆字、掉行。
- 列表列名必须对应第一视觉层级：A2A `来源` 列应优先展示 `source_type`，`last_fetch_status=success` 这类正常内部状态不应出现在列表主位置。
- 列表正常态不要堆解释文案；A2A `来源` 列这类扫描字段应优先只展示短标签，只有失败、未拉取等需要用户注意的异常态才追加状态标签。
- AI Native 中如果 MCP Server 或 A2A Agent 的后端绑定到 Pole 注册服务，列表和详情中的 `namespace/name` 应可点击跳转到注册发现服务详情；自定义地址保持普通文本，避免误导成内部资源。
- A2A Agent Card、MCP tool schema 这类 JSON 契约不应默认直接铺满抽屉；默认应按领域字段做可视化渲染，原始 JSON 只作为用户主动切换的调试/排障视图。
- A2A Agent Card 这类可视化契约详情不能只追求信息密度；默认视图应保留契约文档的阅读节奏，用标题、关键信息网格、能力分区和 Skill 卡片组织内容，避免压成生硬的 inspector。
- 优化详情页不能只追求信息密度；A2A Agent Card 这类契约阅读页需要保留文档化节奏、主标题和卡片分组的可读性，不能压成硬边框 inspector，否则会比原设计更生硬。
- A2A Agent 技能和 MCP Tool 一样属于能力/API 浏览场景；详情抽屉里不要默认用大表格展示少量技能，应使用目录 + 详情的能力浏览器结构，让用户直接读到描述、标签、输入输出、示例和安全声明。
- 控制台资源列表的身份列和操作列必须优先固定可见；不要为了展示更多字段牺牲操作可达性。中间列应通过稳定列宽、单行摘要、省略和紧凑扫描单元控制，尽可能让常见桌面宽度无需横向滚动即可查看全部信息。
- 优化控制台资源列表时不能只检查功能和数据是否展示；表头是否换行、标签是否撑高行、计数字段是否拆行、分页是否和表格边界对齐、操作图标是否过散都属于交付质量，需要用页面级样式和验证脚本固定。
- Console 品牌标识应优先展示产品品牌 `Pole.IO`；不要在主 logo 文案里追加 `Console` 这类功能后缀，除非用户明确要求区分多个产品线。
- 本地 all/console 模式下，`console/web/dist/index.html` 是启动时由 Gin `LoadHTMLGlob` 加载的；执行 `npm run build` 后必须重启 all/console，否则 8080 可能继续返回旧 index，进而请求已不存在的 hash 资源并导致页面打不开。
- 新增治理规则详情时，操作按钮不能另做内容底部 sticky footer；应复用 `RuleDetailDrawer` 内的 `StickyTool + RuleStickyAction`，否则按钮位置会和既有治理详情不一致，并可能影响抽屉正文滚动体验。
- 治理工作台这类仪表盘页面不应让整个主页面随列表长度滚动；应固定页面视区高度，让清单面板内部的表格内容区滚动，保持页头、汇总、筛选和分页稳定可见。
- 新增治理规则类型的查询接口不能只返回业务对象；auth interceptor 必须像既有路由、限流、熔断等规则一样在列表和详情响应里回填 `editable/deleteable`，否则 proto bool 默认 false 会让 Console 误判为无编辑权限。
- 新增治理规则详情不能只把查看态做成结构化展示，编辑态也必须同步产品化；不要用规则数组或元数据 JSON Textarea 作为编辑态占位，用户点击编辑应看到和查看态同一信息架构下的字段控件。
- 治理规则编辑态不能只做到字段结构化；还要做视觉质量验证。抽屉宽度、FormItem 标签方向、规则块层级、条件行换行、表格列宽都要用真实 8080 页面截图和布局指标检查，避免“能编辑但很丑”的临时表单感。
- 调用鉴权这类策略型治理规则不应设计成普通表单堆叠；应参考限流、熔断的规则块模式：header 展示 `规则 [n]`、摘要和动作，正文按接口范围、鉴权结果、匹配条件分区，并支持折叠。
- 治理规则的规则级 `metadata` 在 Console 产品文案中应优先称为“规则标签”；不要在新增规则详情里直接暴露“元数据”这种技术字段名，除非是通用资源元数据管理场景。
- 治理规则基础信息区应承载规则标签，不要把规则级标签拆成和策略定义并列的独立大卡片；编辑态要按身份、开关/优先级、作用范围、标签、描述组织栅格，而不是平均两列铺满。
- 治理规则 spec 的最外层规则对象不要保留 `namespace` / `service` 字段，也不要用注释解释这两个字段迁移到哪里；规则归属和作用范围应由规则内部结构表达，`metadata` / 规则标签只表示扩展标签。删除字段时也不要用 `reserved` 占位，治理规则字段号可以重新从 1 开始连续整理。
- 治理规则 spec 不应保留仅用于 Console 展示的扩展 map 字段，例如 `FaultDetectRule.extendInfo`；展示需要应由 Console 自己从规则结构推导，删除字段号用 `reserved` 保留即可。
- 限流窗口这类由数值输入和单位下拉组成的复合控件，单位 `Select` 必须绑定当前行的 `validDurationUnit`；不能只在 `onChange` 中写回，否则编辑态会显示占位“请选择”，让用户误以为数据缺失。
- 治理规则详情保存更新成功后，如果抽屉不关闭，就必须自动回到 readonly 状态；不能继续保留 `保存 / 撤销` 和输入控件，否则用户会误以为保存未完成或仍处于未提交编辑中。
- 治理规则交互修复不能只改用户截图中的单一规则类型；路由、限流、熔断、探测、无损、泳道和新增流量治理都要按同一产品行为横向检查，尤其是保存后状态、表格编辑缓存和创建/更新的抽屉关闭语义。
- 用户指出“所有治理规则都要考虑”时，验证范围必须覆盖路由、限流、熔断、主动探测、无损、泳道、调用鉴权、流量镜像、流量 Mock；不能把某个类型通过当成整体通过。
- 治理规则编辑器的布局必须直接复用 `shared/governance.module.less` 的既定范式（基础信息 = `infoGrid` 12 栅格 + `field`(span4)，描述/规则标签各自 `field full` 独占整行；分组内多字段用 `kv2`），不要在 Security 等新模块里另写 `formGrid/editGrid` 这套 6/2/2/4 私有列宽。否则规则标签会被挤到和命名空间同一行、子规则字段也对不齐。对齐已有模块的栅格是默认共识，不应等用户反复提醒。
- 修“布局奇怪”这类反馈要从范式层重写（直接换成共享栅格组件/类），不要靠逐处调 padding、改单个 class 打补丁；补丁只会让两套体系并存、问题反复出现。
- 设计 E2E 测试用例时必须先确认测试边界：如果用户明确说“只考虑接口维度”，就不要默认加入 Playwright、浏览器、DOM、截图或 Console 前端交互测试能力；此时闭环应覆盖 8080 Console API 读写、8090 Client API 查询可见性、权限策略生效和 `consoleOpen/clientOpen` 配置开关矩阵。
- 治理规则编辑器的信息架构要按该规则类型的“操作心智”组织，不能照搬 proto 字段平铺：流量镜像应是 接口范围 → 流量匹配(来源服务也属于流量标签) → 采样比例 → 镜像目标 的四步语义，用 `shared.step` 轴呈现，与鉴权策略卡一致。这是默认共识，不应等用户反复提醒。
- 镜像规则的 `MirrorSource` 原本没有 `API` 接口字段（Mock 有），按需对齐时直接改 `specification/api/v1/traffic_manage/mirror.proto` 追加 `API api = 4`，在 `source/go` 下 `bash build.sh` 重新生成；后端整 proto JSON 序列化（`protojson` 存 `governance_rule.rule` 列），store/service/cache 零改动即自动持久化回环。
- 本地联调 spec proto 改动用 `replace github.com/pole-io/specification => 本地路径`（path-replace 跳过校验和，无需改 go.sum）；**严禁直接跑 `go mod tidy`**——它会顺带升级 envoy/genproto 等间接依赖，打断 xds 等无关代码编译。只手动追加 replace 行即可，正式合并前需 spec 发版并改回版本号。
- 调用鉴权规则只按命中策略执行动作；spec、Console、测试数据和示例 JSON 都不应保留“未命中默认动作”字段，也不要为了兼容 UI 再补回该字段。
- 鉴权、流量镜像、流量 Mock 的规则归属统一绑定被调服务；来源服务只能放在 `TrafficMatchRule` 的 `CALLER_SERVICE` 等匹配条件中，不要再把 source namespace/service 当成规则索引或发布下发的服务归属。
- 当治理规则的产品语义从“目标服务 + 隐式匹配条件”收敛为 `Caller -> Callee` 时，不能只改 Console 展示；必须同步核对 `../specification` 真源契约，让 proto 顶层也能表达 caller/callee，再让 control-plane 做兼容读取。
- 流量镜像的页面心智必须像路由一样先表达 `caller -> callee`：spec 顶层用既有 `SourceService caller` 和 `DestinationService callee` 表达两端，caller 可选“全部服务”，子规则只保留接口、流量匹配、采样比例和镜像目标，不应让用户在子规则匹配条件里手动拼来源服务。
- 服务 Mock 的页面心智也必须像路由和镜像一样先表达 `caller -> callee`：spec 顶层用既有 `SourceService caller` 和 `DestinationService callee` 表达两端，caller 支持“全部服务”；Mock 子规则只表达接口、流量匹配和响应结果，不应让来源服务藏在子规则条件里。Caller 状态只能是“全部服务”或“具体 namespace/service”，不要保留“某 namespace 下全部服务”这种半状态。
- 治理规则编辑抽屉的主空间只服务于规则表单；不要添加右侧实时 Spec、YAML 或 JSON 预览列。长内容由表单内部滚动承载，不能退化成页面整体滚动。
- RouteRule 等复杂规则的抽屉宽度必须优先保障表单可读、无横向滚动和标题正常横排；移除动态 Spec 后不得保留空预览列或双栏尺寸约束。
- 治理规则动态实时 Spec 预览移除后，宽抽屉不应继续沿用双栏时代的 `min(1560px, calc(100vw - 40px))`；路由、泳道、熔断、主动探测等复杂单栏编辑器统一使用 `clamp(860px, 60vw, 1180px)`，默认治理抽屉仍保持更紧凑宽度。不要直接降到 50vw，否则多列表单和接口条件容易被重新挤压。
- 治理工作台的统一列表不能只给某一个规则类型提供新建入口；新建规则必须是清单头部的常驻主操作，并通过下拉菜单选择具体规则类型打开对应 editor 的 `op="create"`，同时清理上一条规则的 Redux 编辑态。不要把创建动作绑定到当前筛选必须只选中单一类型。
- 治理工作台规则清单不能把标题、类型按钮、搜索框和所有操作硬挤在同一行；这会导致类型按钮被裁切、扫描路径混乱。规则类型筛选应使用一个多选下拉框，空值表示全部；搜索、命名空间、服务和重置在同一筛选工具栏内排列。
- 治理工作台清单头部和筛选工具栏里的工具操作优先用 TDesign 图标按钮，例如新建用 `AddIcon`、刷新用 `RefreshIcon`、重置筛选用 `FilterClearIcon`；图标按钮必须保留 tooltip 和 `aria-label`，不要用大块文字按钮挤占工具栏空间。
- 治理工作台清单筛选栏应保持轻量：如果命名空间和服务筛选没有明确高频价值，不要保留两个大下拉框占位；优先保留规则类型多选、关键词搜索和右侧图标操作组，新建/刷新/重置放在同一工具栏里。
- 治理工作台规则列表应采用管理清单视图：规则列展示名称和摘要，类型列用轻量彩色标签，作用对象独立展示，右侧展示创建时间、更新时间、状态点和行内操作；不要把匹配条件、发布状态等技术细节铺成过多主列。
- 治理工作台规则列表的行操作必须对齐服务列表规范：使用 `Tooltip + Button shape="square" variant="text" + TDesign icon`，不要用文字链接承载编辑、详情或删除；删除仍应包 `Popconfirm`。
- 治理规则清单行内不要同时放编辑和查看详情两个近似入口；保留一个 `查看 / 编辑` 图标进入详情抽屉，具体编辑动作交给详情抽屉标题区承载。
- 治理编辑抽屉左侧“内部滚动”不能只看 CSS 写了 `overflow:auto`；必须验证真实 `scrollHeight > clientHeight`，并通过 wheel 或设置 `scrollTop` 确认滚动发生。若左侧是 column flex，直接子 section 需要 `flex: 0 0 auto`，否则 section 会 shrink 后被共享卡片的 `overflow:hidden` 裁掉，外层不会产生滚动。
- 治理规则编辑抽屉双栏交互不是单个规则类型的局部样式问题；修复路由、限流、熔断这类共性行为后，必须同步沉淀到 [[patterns]] 的长期技术约定，后续新增或重构规则编辑器按该约定验收，避免用户按规则类型重复指出同一问题。
- PRD 明确要求“数字输入 + 单位后缀”和曲线可视化时，不能只通过字段、文案或空容器判定完成；必须在真实页面确认数值和单位同时可读、曲线按算法实际绘制出来。TDesign 数字单位优先复用 `InputAdornment append`，避免 `InputNumber suffix` 在治理抽屉里把单位显示成输入值。
- 治理规则编辑抽屉的共性布局缺陷被用户指出一次后，必须主动横向审计所有同构编辑器，包括主动探测这类文件位置复用 `CircuitBreaker/` 目录但交互独立的编辑器；不能只修当前截图或当前规则类型后就宣称同类问题已处理。
- 协议专用配置区不能为了省事直接复用通用标签/元数据控件；例如主动探测 HTTP Headers 虽然数据结构是 `Label[]`，页面也必须按 PRD 呈现 `H` 标识、Headers 说明、键/值/操作三列表和对应底部计数，避免把业务协议配置做成泛化标签编辑器。
- 列表型编辑器的草稿归一化不能提前过滤空行；“添加一行”通常需要先创建 `{ key: '', value: '' }` 这类空草稿，保存校验再拦截空值。如果在 normalize 阶段过滤空草稿，用户点击添加会表现为完全无效。
- 参照 PRD 截图调整局部模块时，不能直接按截图观感放大控件；最终字号和控件高度必须回到当前治理抽屉的设计系统规格，例如字段值 14px、辅助说明/列头 12px、默认按钮和输入高度，避免局部模块显得比其它表单大一号。
- RouteRule 编辑抽屉不需要额外的底部操作/校验栏；编辑/发布/保存/撤销继续使用治理详情抽屉既有标题区 `StickyTool`，校验通过字段提示和保存失败通知表达。
- RouteRule 编辑抽屉的「服务范围」标题区必须按 PRD 的展开/收起两态实现：展开态标题同行显示 `主调方 → 被调方`，收起态标题同行显示 `namespace/service → namespace/service` 摘要；不要额外放说明文案或右侧独立摘要。
- RouteRule 编辑抽屉里的折叠态 section 不能沿用展开态的大块 header 高度；折叠后应是紧凑单行摘要，注意 CSS `min-height + padding` 在默认盒模型下会叠加撑高。
- RouteRule 编辑态的目标分组表不能把实例标签退化成普通文本输入；应保留 chip 展示和“编辑标签”弹窗。权重列必须给 `InputNumber` 足够稳定宽度，分组名称由顺序自动生成 `Group {index}`，不要让用户手填。
- RouteRule 基础信息编辑区的同一行字段应使用 TDesign `Row/Col` 这类稳定栅格控制比例，例如规则名称/优先级/状态按 8/2/2 排布；不要只用 `1fr + 固定列` 让名称输入框吞掉空间，造成右侧字段间距割裂。
- 保存 payload 的正确性由 service 边界、请求测试和保存结果验证，不在编辑器展示产品态或伪造的实时 SPEC。
- 限流等后续治理规则编辑器必须复用 RouteRule 已验证的单栏滚动模型：正文固定可用高度，`formPane overflow:auto`，不再保留独立 Spec 列或为预览设置 viewport 高度。
- RouteRule 匹配条件里的参数键是用户业务数据，不应按参数类型预置 `x-tenant`、`$method`、`session` 等候选；参数类型只决定来源类型，参数键用普通输入框让用户自行填写。
- RouteRule 匹配类型为 `包含/不包含` 时，匹配值应使用 TDesign `TagInput` 做多值编辑；保存给后端的 `value.value` 仍是英文逗号分割字符串，不要让用户在普通 `Input` 中手写分隔格式。
- RouteRule 目标分组的实例标签同样是 `MatchString`，标签值在 `包含/不包含` 时也必须使用 `TagInput`，并按英文逗号拼接回写；不要只修匹配条件表而漏掉标签编辑弹窗。
- 治理规则编辑抽屉的视觉验收不能只看 Playwright snapshot 或 DOM 文本；涉及固定高度、滚动和双栏布局时必须截真实 8080 页面截图并检查关键卡片 rect，尤其不能在 `RuleDetailDrawer` 的 Tab 内容里再套 `100vh` 高度和多层 `overflow: hidden` 导致 section 内容被裁切。
- 熔断规则 spec 调整时，`BlockConfig` 只承载熔断策略的接口、错误判断和触发条件；`max_ejection_percent`、`recoverCondition`、`faultDetectConfig`、`fallbackConfig` 这类策略执行配置应放在 `CircuitBreakerRule` 与 `BlockConfig` 之间的中间消息中。删除旧字段时按治理规则当前约定重新压实 `CircuitBreakerRule` field id，不要再加 `reserved`。
- 熔断规则的 `level` / 熔断粒度是创建时确定的规则级语义，编辑已有规则时必须只读展示，不能在编辑态继续提供切换控件；同时熔断列表和治理工作台的熔断筛选态都应有明确的“新建熔断规则”入口。
- specification 这类协议仓库 PR 应只包含协议源文件和既有生成产物；不要为单次变更新增临时校验脚本或未被仓库约定的辅助工具。需要额外校验时在本地执行并写入 PR 验证记录，除非用户或仓库维护规范明确要求提交脚本。
- 用户说“治理规则里面的 Code 统一为 string”时，范围只限治理规则响应效果字段，例如熔断 `FallbackResponse.code`、限流 `CustomResponse.code`、Mock `MockResponse.code`、鉴权拒绝效果 `TrafficSecurityRejectEffect.code`；这些响应效果里不应保留 `status_code`。不要扩展到 `model.Response`、`DiscoverResponse`、`ConfigDiscoverResponse`、心跳响应或限流器协议响应。
- Mock 响应效果中 `body` 已表达被 Mock 出来的响应内容，不应再保留 `message` 这类重复正文/错误说明字段；鉴权拒绝效果没有 `body`，可以保留 `message` 表达拒绝原因。
- 主动探测规则的服务信息属于规则级：`FaultDetectRule.target_service` 在 `FaultDetectSubRule` 之上；`FaultDetectSubRule` 只承载协议、端口、间隔、超时和协议配置等探测参数。客户端发现响应不需要 `FaultDetector{rules, revision}` 包裹，直接用 `DiscoverResponse.faultDetectRules[]`，聚合 revision 放在 `DiscoverResponse.service.revision`。
- 主动探测 Console 的「被探测对象」只展示和编辑服务信息：命名空间与服务。接口名称、接口匹配类型、接口协议和方法不属于该 section；如果协议需要保留兼容字段，也不要在页面主路径暴露成被探测对象的一部分。
- 当用户明确说“现在讨论的是最终效果，不考虑新老 spec 兼容”时，协议 PR 不应保留 Deprecated 字段、兼容注释或 fallback 语义；例如流量镜像和服务 Mock 应直接用顶层 `SourceService caller -> DestinationService callee`，删除旧 `target_service`。
- 流量镜像和服务 Mock 的最终 spec 不需要配置持续时间；不要保留 `MirrorRule.duration`、`MockRule.delay` 或仅用于这两个字段的 `google.protobuf.Duration` 依赖，删除后按最终字段号压实。
- 调整治理规则 spec 时优先复用已有领域端点类型；流量镜像和服务 Mock 的 caller/callee 不要新增 `ServiceScope`，直接使用既有 `SourceService` / `DestinationService`。
- 按设计交接文档调整流量镜像编辑抽屉时，第三段必须是「镜像规则」子规则列表：每条子规则按接口范围、多流量标签和镜像执行三步组织；不要继续沿用旧的全局目标服务、持续时间、目标实例标签、实时 Spec 预览，或把 caller 写进子规则匹配条件的 UI。
- 治理规则的 caller -> callee 服务范围区应复用共享 `ServiceScopeSection`：RouteRule、熔断、流量镜像和服务 Mock 都应使用同一套紧凑标题、折叠摘要、主调/被调卡片和方向连接器；规则类型特有配置通过插槽追加，不要在各编辑器里重新手写四字段平铺表单。
- 治理规则编辑器里的数字输入框统一使用 TDesign React `InputNumber theme="normal"` 无按钮形态；不要使用默认 `row` 或 `column` 加减按钮样式。新增或调整治理规则编辑器时必须跑 Governance 数字输入静态校验，避免局部控件突兀。
- 路由、限流、流量镜像、服务 Mock、调用鉴权和泳道的流量匹配条件必须复用共享 `TrafficMatchConditionEditor`；不要在各规则里重复手写四列条件表、AND/OR 分段控件或私有匹配值编辑器。参数键仍由用户输入，参数类型切换不能自动填业务示例键。
- 泳道组入口和组内服务选择不能把命名空间与服务名拼成一个下拉项；必须用两个独立下拉框分别选择命名空间和服务。组内服务添加要保持与入口表格一致的行内选择体验，但只能从普通服务池里选服务，不能混入网关入口类型。
- 在共享匹配条件头部放置额外控件时，必须给右侧 action 区和额外控件都设置稳定宽度与 `min-width: 0`，尤其是 TDesign `InputAdornment + InputNumber` 组合；否则 `%` 后缀、数字输入框和 AND/OR 分段控件会在泳道窄卡片里互相挤压错位。
- 限流规则接口范围已从旧 `LimitTrigger.method: MatchString` 收敛为 `LimitTrigger.apis: repeated API`；前端可读取旧 `method.value` 字符串作为兜底，但编辑、预览和提交都必须基于 `apis[]`。匹配类型为 `包含/不包含` 时路径值仍要使用 TagInput 多值编辑并按英文逗号写入 `API.path.value`。
- 治理规则里凡是“一个子规则/策略使用同一套条件和动作覆盖 API 范围”的场景，应优先使用 `repeated API apis` 表达多个接口资源；不要用单个 `API api` 迫使 Console 复制子规则。限流、熔断、调用鉴权、流量镜像和流量 Mock 都按这个标准横向核对，新增接口按钮应追加当前子规则/策略内的 API 行。
- 治理规则编辑抽屉不再展示动态实时 Spec/YAML/JSON 预览；路由、限流、熔断、主动探测、无损、泳道、调用鉴权、流量镜像和流量 Mock 都应把主空间留给表单本身。需要校验时保留保存前校验和错误通知，不要重新加右侧 Spec 预览列。
- 新增治理资源类型时，鉴权适配必须横向补齐四条链路：策略资源字段映射、操作鉴权资源收集、策略创建/更新资源存在性检查、策略详情资源摘要回显。不能只补 `auth_checker` 或发布资源收集，否则会出现不存在资源可授权或详情无法回显的问题。
- 认证管理详情从页面迁到抽屉时，不能把旧详情页的“权限信息、关联策略、成员、资源树、接口范围”等权限视图压扁成基础字段或禁用表单；抽屉应保留原有权限信息架构，只改变承载方式。
- 修复认证策略详情缺数据时，必须用真实 admin 默认策略同时校验列表接口和详情接口响应形态；当前详情接口的 `data` 可直接是 `AuthStrategy`，前端 service 不能只认 `{ authStrategy }` 包裹。主体权限信息里的关联策略名称也必须能继续打开策略详情抽屉，不能只是静态 Link。
- 配置中心分步抽屉不能在最终提交时读取已经卸载的前一步 `FormItem` 字段；进入下一步前必须缓存元信息，尤其是配置文件创建的 `name/comment/encrypted/encryptAlgo/tags`，否则后端会收到空 `name` 并返回 `400103 invalid parameter`。
- 配置中心前端 service 必须以当前后端生成 proto JSON 字段为准做边界适配；发布配置这类写请求要把页面 camelCase 的 `fileName/releaseDescription/releaseType/betaLabels` 转成后端 snake_case 的 `file_name/release_description/release_type/beta_labels`，不要让页面层直接感知后端字段。
- 配置文件页不能只依赖从配置分组列表点击时写入 Redux 的 `editGroup`；刷新或直达 URL 时必须按 `namespace/group` 补拉配置分组，并且只使用与当前 URL 匹配的分组权限，避免新建入口不可用或误用旧分组权限。
- 配置发布抽屉使用 Monaco DiffEditor 时，要给 original/modified 设置不同稳定 model path，并避免步骤切换卸载时主动 dispose 当前 model；否则会在版本对比切换到发布信息时报 `TextModel got disposed before DiffEditorWidget model got reset`。
- AI 工具里的 MCP Server 和 A2A Agent 是独立资源，不应借用 Services 或 PolicyRules 做授权；接入前必须先更新 specification 的 `ResourceType` 和 `StrategyResources`，再补 control-plane 的资源映射、存在性校验、详情回显、操作鉴权和 Console 授权入口。
- 为 `StrategyResources` 新增资源类型时，不能只更新 proto、编辑器和新建默认策略的资源枚举；已有“全资源”系统策略和主账号默认策略不会自动获得新的 `id="*"`。必须对语义明确的历史全量默认策略做幂等回填，并以真实策略详情和缓存通配匹配验证“覆盖新增资源”可授权未来创建的资源；不得借此扩大普通自定义策略的资源范围。

- 用户明确要求 Pebble 存 protobuf marshal 后的 bytes 时，设计目标是实例列表、配置、契约和治理规则这类可重建大 value 的低分配读取；不要把它降级成普通 Go 对象缓存，也不要让实例心跳进入同步磁盘写热路径。实例列表 key 必须包含 revision 与过滤/权限可见性 hash。
- 客户端大数据卸载到 Pebble 必须以开关形式实现，默认仍走当前内存路径；开启后也必须用基准证明服务发现、配置发现、服务契约和治理下发的稳态性能不低于当前实现，未达标的 domain 不能纳入卸载范围。
- 配置文件、服务契约和 OTel event/audit 本地队列都应优先使用 Pebble；不要再为这些能力新增 bbolt 实例。配置/契约是 value cache 语义，OTel 是 append/ack/delete queue 语义，两者可以共用 Pebble 引擎但必须用不同抽象和 key prefix 隔离。
- 移除某个本地存储组件时，不能只改生产代码和 `go.mod`；测试套件默认配置、fixture 文件、历史 helper 和 `go.sum` checksum 也要一起检索清理，避免旧 store 模式在后续测试中被误复活。
- 服务调用鉴权解决的是数据面服务间信任，默认不能退化为用户填写 Header value。应由 control-plane 为每个服务托管不可见、不可修改的内部身份，并向通过 workload bootstrap 的实例签发可轮换短期凭证；自定义 Header/value 只作为显式兼容模式。
- 设计服务身份时必须把“稳定身份标识”和“不可伪造的身份凭证”分开；隐藏服务 ID 不能替代认证。调用方只拿自己的凭证，被调方只拿验证材料和规则，不能通过按 callee 下发的治理规则泄露其它服务的 credential。
- 服务调用鉴权的安全边界必须在被调方入站 SDK/sidecar；调用方 SDK 自己执行 Header matcher 或 `ALLOW/DENY` 可以被绕过，只能作为提前失败优化，不能宣称已建立服务间信任。
- Pole service token 只负责 SDK 与 control-plane 之间的客户端认证，不能等同于数据面 `ServiceIdentity`。正确链路是 token 先证明 SDK 有权代表某服务，再由 control-plane 通过 Discover 下发该服务身份描述；实例级数据面 credential 另走不可共享缓存的签发/续期接口。
- 深色主题验收不能只确认 Fluent Provider 已切换；页面级 LESS 的 `color`、`background`、`border` 等硬编码会覆盖语义 token。批量迁移后要额外检查主题变量是否出现自引用，并以真实浏览器覆盖列表、详情抽屉、筛选控件和空态。
- 用户明确控制面 TLS 按需时，不要把安全最佳实践升级成托管身份功能的强制前置条件。SDK 与 control-plane 应同时支持 `grpc` 和 `grpcs`，文档说明明文 bearer 的风险并推荐生产启用 TLS，但最终由部署方按环境选择。
- 错误提示不能将业务码、后端消息和 Request ID 拼成单个 `Error.message`。请求层应传递独立的 `code/message/requestId`；Toast 正文格式化展示错误码和国际化消息，Request ID 只允许单独复制，并提供包含这三项的格式化 JSON 复制入口。
- Toast 的自动关闭不应替代手动关闭。所有成功、错误通知应使用独立 Toast ID，默认 10 秒自动关闭，并始终在 Fluent 标题区提供可访问的关闭按钮。
- 当错误 Toast 已提供完整 JSON 复制时，不要再并列暴露 Request ID 和 JSON 两个底部大按钮；将唯一的“复制”动作放到标题右上角，保留图标、短文案和关闭按钮即可。
- 精简 Toast 操作区后，不能只依赖 Fluent 默认 292px 容器宽度；应显式设置受视口约束的承载宽度，并让正文跨越默认网格的尾列。每次调整后都要用真实长中文错误消息确认既不早换行、也不裁切右侧操作。
- 用户明确移除治理规则实时 Spec 后，必须横向核对路由、泳道、限流、熔断、探测、无损、鉴权、镜像和 Mock 的渲染、样式与回归脚本；不能只修截图中的当前编辑器，或保留会诱导回归的旧约定。
- 治理规则的重复字段行不能按浏览器视口假设列宽；必须按真实内容区验证最后一列和操作按钮不溢出。服务选择被标为“搜索”时，输入必须实际过滤候选项，且选择器保持紧凑宽度、编辑器内容较少时不应被固定高度拉满。
- API 的 `protocol/method/path` 统一存储结构不等于统一编辑交互：HTTP 的 `method/path` 是请求方法和 URI，gRPC 是方法名和服务名，Dubbo 是方法名和接口名。协议切换必须重置旧协议的值，并以专项回归和真实页面确认 RPC 行不再保留 `GET /`。
- RPC 规则的编辑顺序必须体现选择粒度：先选择 gRPC 服务或 Dubbo 接口，再以可空的方法名收窄；不要将方法放在服务/接口之前，也不能把 RPC `method` 误设为前端必填项。
- RPC 编辑器不能把“表单顺序正确”误当成“字段语义表达清楚”：存储中 `path` 是 gRPC service/Dubbo interface，`method` 才是可选方法。表头必须直称“RPC 接口”“RPC 方法（可选）”，且接口列要明显宽于方法列；否则即使提交数据正确，用户仍会合理地怀疑字段被写反。
- 鉴权服务信息是有先后依赖的上下文选择器：先命名空间、后服务名称，不能因宽画布把它们拆成两列。该段必须复用统一的可折叠组件，收起时给出已选服务摘要，避免用户丢失当前选择。
- 鉴权编辑器的每个主要步骤都应使用一致的折叠模型；认证方式不能成为唯一不可收起的长表单。折叠摘要必须来自当前认证模式，且不应暴露 Header 值等凭证内容。
- 请求匹配的“参数类型”和“值来源”是两个独立维度：Header/Query/Cookie 等决定从哪里取键，“固定值/请求参数”决定如何使用取到的值。请求参数必须表示采集当前键的实际值并交给下游治理动作；限流按该值隔离计数器，路由按同名 key-value 匹配目标标签，不能把它误解成 API path 字段、另一个参数键或机器环境变量。
- 当交付结果需要用户在当前回合结束后继续打开本地页面时，不能把服务只留在 exec/PTY 工具会话中；必须使用 tmux 等独立后台会话，并在结束前确认会话存在、8080/8090 监听、真实业务路由和静态资源均为 200。
- Pole Console 的 Agent 工作台不能退化成挂在“AI 工具”分组下的资源表单。Agent 是独立一级产品入口，主交互必须是用户与 Agent 对话；资源查询、创建、修改由 Agent 通过 Pole MCP 工具执行，工具调用过程可展开，写操作先生成临时视图供用户确认，确认后只创建草稿并停在待发布状态。
- 普通控制台与 Agent 不应作为两个互不相干的菜单入口：应在全局页头表达为同一产品的两种工作模式。普通资源页负责精确编辑与发布，Agent 负责对话和工具编排；两者通过安全的资源引用与 `returnTo` 双向交接，不能复制权限、API 或把资源正文塞进 URL。
- Console 新构建上线后，不能只检查服务端 `index.html` 已更新就认为用户标签页已经切到新 SPA；旧文档仍可继续运行旧路由和布局。SPA 入口及所有深链 fallback 必须禁止缓存，验收时要先识别页面加载的资源哈希，再用真实浏览器点击验证关键模式往返。
- Vite 构建会替换 `dist/assets` 时，已打开标签页中的旧主包可能在后续懒加载时请求已删除的旧哈希 chunk；即使 `index.html` 已禁止缓存也无济于事。跨工作区/模式切换应使用整页导航重新取得匹配版本，或在部署层采用原子发布并保留旧资源；排查空白页必须检查 DevTools 中的动态模块 404，不能只看路由地址和 DOM 是否存在。
- Agent 既然是与普通控制台并列的工作模式，就不应继续混在侧栏顶部的资源导航中。模式入口应放在侧栏固定底部、版本信息上方，并在普通控制台显示“进入 Agent 工作台”、在 Agent 会话侧栏对称显示“返回普通控制台”；资源菜单滚动时该入口仍须固定可见，不能因为 Agent 模式隐藏普通资源菜单而失去返回路径。
- 设计 Console Agent 时必须把 `PoleAgent` 建模成一等深模块，而不是把 ModelPort、MCP client、Workbench 平铺成页面或外部编排器需要拼装的零件。页面只与 Agent 会话 interface 交流；Agent 内部拥有版本化 System Prompt、LLM、MCP 工具导入、model-tool loop、会话记忆和 approval resume，现有 Workbench 只负责不可绕过的确定性变更确认。
- Pole Agent 不能只有单次消息时间线和“新会话”清空按钮。工作台应采用 ChatGPT 式会话产品结构：左侧可创建、切换、重命名和删除本地会话，主区保持连续消息流和底部输入框；会话、消息、输入草稿及每会话记忆设置保存在浏览器 IndexedDB。记忆设置必须真实控制发送时使用的历史窗口，不能只做装饰开关；服务端提案与发布安全边界仍独立于浏览器历史。
- Agent 模式已经拥有产品级左侧栏时，会话管理必须直接接管该侧栏，不能在内容区再嵌套第二条会话栏。Agent 页只保留一个对话画布；新建、切换、重命名和删除会话都在最左侧完成，标题栏不再重复“新会话”，空态也不堆叠大块建议按钮。
- Console 登录页不能用超大营销标题、裸露默认账号、悬空输入框和弱描边按钮拼成未完成的宣传页。登录主任务必须放在清晰面板中，主按钮使用明确的品牌色，产品说明克制且不挤压表单，并以真实桌面和窄视口截图验收。
- 用户质疑 Kubernetes 页面未更新时，不能只引用 rollout 成功或截图作为证据；必须同时核对运行 Pod 的 imageID、Pod 内 `index.html`、Gateway 返回内容与资源哈希，并对域名、localhost、LoadBalancer 等实际入口做一致性比对。必要时显式 restart 后用新 Pod 启动时间复验。
- 用户说“仍然查看不到”并提供控制台截图时，先从截图识别其实际停留页面，不要继续重复证明服务端已经更新。应核对浏览器真实 URL，并直接在可见新标签页打开目标深链；已登录控制台截图只能证明用户仍在业务页，不能证明 `/login` 返回旧页面。
- 用户明确把下一步切换到 System Configuration Phase 1 时，必须停止继续打磨上一阶段的登录页并以新目标重新建立计划；交付说明要区分“已实现的新功能”和“上一任务遗留验证”，不能让局部 UI 工作吞掉用户确认过的主线。
- 系统配置页面不能因为首期只读就退化成 50 多行的单一总表。配置目录应按“组件 → 领域 → 配置项”组织，领域同时是未来草稿、发布、回滚和生效状态的工作单元；跨领域搜索可以保留，但不能抹平领域上下文。
- Console 的 Agent 领域不能只列 proposal TTL 和上游超时；如果产品定义是 Console 内部拥有 Pole Agent，就必须同时登记 Agent ID、Prompt 版本、LLM Gateway/model/SecretReference、MCP endpoint/工具白名单和明确的当前 runtime mode。配置登记与运行时接通要分别表达，不能把尚未实现的 ModelPort 伪装成已生效。
- Pole 产品中的 LLM API key 等业务 Secret 默认应由 Pole 自己提供 write-only 创建、加密持久化、版本、轮换和审计；不要把 Kubernetes Secret/环境变量误当成最终产品配置入口。基础设施 Secret 只保存 KEK/自举凭证或作为可选外部 Provider，AgentDefinition 只引用版本化 `pole-secret://` 标识。
- 系统配置包含跨组件运行参数和 Secret 元数据，必须默认只允许主账号/admin 访问；前端隐藏菜单和路由守卫不能替代后端接口鉴权，所有查询、草稿、发布、Secret 写入与连接测试都要复用同一个服务端 admin gate。
## 2026-07-22：角色页必须表达固定系统角色，而不是通用角色 CRUD

- 当产品定义 Admin、资源全读、资源全写为内置角色时，不能只在前端隐藏编辑/删除按钮；数据库必须幂等存在，服务端必须拒绝增删和权限定义变更。
- 角色页只维护系统角色与用户/用户组的绑定关系；角色名称、描述、权限集合与系统标识均不可编辑。
- 新增系统角色会放大角色缓存的定时读取频率，必须验证 Store 读事务都能释放连接；`fetchRolePrincipals` 这类内部查询若只关闭 rows 而不结束 transaction，会快速耗尽 MySQL 连接池并让登录、主账号查询超时。
## 2026-07-22：发布认证角色改动后必须回归系统配置目录

- 系统配置页出现 `0 / 0` 和全零统计时不能视为无配置空态；这代表定义注册、接口授权、响应映射或组件筛选链路至少一处发生回归。
- 认证与角色改动会影响只允许 `main/admin` 的系统配置请求。发布此类改动后必须用真实 admin 会话检查接口响应和非空领域计数，不能只验证菜单可见与 HTTP 200。
## 2026-07-22：Admin-only 页面必须在路由渲染前 fail-closed

- 用户要求非 admin “连页面都不要展示”时，不能只依赖菜单过滤和页面接口 403；前端路由必须在组件加载/渲染前完成授权守卫并重定向。
- localStorage 中的角色可被旧会话残留或用户修改，不能作为 admin-only 页面与菜单的权威依据。前端启动时必须从 HttpOnly 签名会话读取服务端角色，鉴权未完成时默认隐藏入口并阻止页面渲染。
## 2026-07-22：本地 Kubernetes 是唯一运行验收环境

- 用户指定所有运行测试必须在 Kubernetes 部署后执行时，不再启动或保留宿主机 `pole-server`/Console 进程；8080/8090 若由 OrbStack 监听，属于 Kubernetes 网络入口，不能误杀 OrbStack。
- macOS 上为本地 K8s 构建运行镜像时，不能直接把 `go build` 生成的 Mach-O 放进 Linux 容器；必须显式使用 `GOOS=linux GOARCH=arm64 CGO_ENABLED=0`，并在 rollout 后检查新 Pod 真正 Ready，不能让旧 ReplicaSet 掩盖新 Pod CrashLoop。
- Console 的暗色主题验收不能只检查主题 token 或个别页面：必须从 Kubernetes 实际部署的 SPA 入口逐类抽检详情卡片、统计卡、表格、抽屉、弹窗和空状态，并对可见表面计算背景色/文字色；构建、自动化测试、HTTP 探测和浏览器验收都必须针对 K8s 容器产物，宿主机进程或宿主机构建结果不能作为通过依据。

## 2026-07-23：用户提供参考 HTML 后必须按参考稿做视觉对齐

- 用户给出可运行的视觉参考时，它就是本轮布局、尺寸、层级和交互密度的事实来源；不能继续沿用上一轮的主观“极简”方向或只做局部样式修补。
- 对齐参考稿时应先测量侧栏、顶栏、内容区、上下文面板和输入器，再把既有真实能力映射进去；视觉一致性不能以删除 IndexedDB 会话、记忆设置、MCP 临时视图或待用户发布边界为代价。
- 交付前必须在相同视口并排比较参考稿与 K8s Gateway 实际页面，记录可见差异并修正后再验收。

## 2026-07-23：登录页不重复提示登录事实

- 未认证用户从受保护路由进入登录页时，登录表单本身已经完整表达下一步操作；不要再弹出“当前未登录，请先登录”之类重复 Toast。
- 路由仍可保留来源位置用于登录后返回，但来源状态不能被登录页当成错误；Toast 只用于登录提交失败、会话失效且需要解释原因，或系统检查失败等可操作异常。

## 2026-07-23：Agent 输入器必须覆盖 Fluent 全局聚焦装饰

- Agent 对话输入器是一个组合式表面，焦点反馈只能落在最外层 composer 上；Fluent Textarea 的内层下划线、`focus-visible` outline 和 inset shadow 必须在局部明确关闭，否则会叠成双蓝线。
- 亮色主题下不能用高比例正文色混合边框，Retina 截图会呈现接近黑色的粗框；输入器默认使用弱边框和轻量染色阴影，聚焦态再用低透明度品牌色增强。

## 2026-07-23：Agent 配置存在不等于运行时已经接通

- LLM Gateway、model、Prompt 和 MCP endpoint 出现在 YAML 或系统配置目录时，只能证明定义已登记；只有后端 ModelPort 实际发起请求、tool loop 执行白名单工具并产生真实响应，才能向用户声明 Agent 可用。
- “真正可用”的 Agent 验收必须同时覆盖有工具、无工具、带历史的多轮回复、提案、确认只保存草稿、未配置安全降级；JSON 中前端按数组消费的 `tools` 等字段必须稳定返回空数组且页面仍做空值防御，不能以单轮 MCP 成功代替完整页面闭环。
- Agent 页面不得用静态文案显示“MCP 已连接”或“模型已就绪”。连接状态必须来自服务端运行时探测或当前会话执行结果；未配置、超时、鉴权失败和工具不可用必须 fail-closed 并可诊断。
- 前端本地正则可以作为原型或降级提示，不能冒充内部 Agent。正式链路中页面只发送会话消息，System Prompt、模型选择、工具 schema、工具执行和审批暂停/恢复全部由 Console 后端 PoleAgent 深模块拥有。
- Pole Agent 的 LLM Gateway 地址、模型、Prompt、工具策略和 API key 属于 Pole 产品配置，不应要求管理员以 Kubernetes env/Secret 作为日常配置入口。目标闭环必须由 Pole 内部 Admin 页面、数据库版本、加密 Secret、发布快照和运行时热加载共同完成；K8s 只保留数据库连接与根加密材料等最小自举配置。
- System Configuration 的 Agent 领域不能把通用配置目录表格、状态标签、编辑按钮和发布按钮堆在同一工具栏；Agent 是完整配置任务，应使用专用工作区呈现连接、能力、指令、Secret 和发布状态，普通表格只服务只读目录。测试连接、保存草稿和发布必须在视觉层级上表现为连续但不可合并的三个阶段。
- 用户要求重设计“系统配置编辑”时，不能把范围收窄为当前最显眼的 Agent 领域。必须逐一审查 Pole Server 与 Console 的所有领域和字段，明确哪些可动态编辑、哪些需重启、哪些只能部署修改，并为所有可编辑领域提供一致的草稿、校验、差异审阅和发布闭环；领域特化只覆盖特殊交互，不替代通用能力。

## 2026-07-24：全站体验整改不能停在审计报告

- 用户要求一边测试一边修复时，审计结论只是缺陷队列的起点；必须从共享根因开始实现、重建真实运行环境并逐页复验，发现新问题继续进入下一轮修复。
- “页面没有布局、样式、体验问题”不能由静态检查或少量截图推断；至少要覆盖全部可见业务域、核心创建/编辑入口、桌面与窄视口、亮暗主题，以及按钮是否触发真实请求或导航。
- 服务实例详情页验收不能只确认抽屉能打开和字段有值；必须检查标签与值的阅读顺序、字段网格在宽抽屉中的对齐、空值密度，以及拥有 `editable` 权限时是否存在清晰可达的编辑入口，并实际完成进入编辑、撤销和保存流程。
- 全站表格规范必须由共享组件默认保证，页面只能声明业务列宽和特殊固定列；不能依赖每个页面重复补丁，也不能用 `overflow-x: hidden` 掩盖列宽冲突。
- 可增删的 Grid/Row 只要用列头表达字段语义，就必须按表格规范处理：在自身容器内横向滚动、保留列头、固定首列和操作列；窄屏直接隐藏列头再堆成无标签输入框，会让布局看似不溢出但交互语义丢失。
- 表单“重置”验收不能停在按钮 click 成功或 FormStore 值变化；受控 Input/Textarea 必须验证实际 DOM value 恢复。值从字符串回到 `undefined` 时同样要同步为空，否则公共控件会让所有新建表单出现假重置。
- 聚合加载多个授权对象时，单个接口失败不能让抽屉永久 Loading；应使用有界单页请求与 `allSettled` 收敛，展示可用的部分数据、报告失败项，并在所有路径明确结束 loading。
- 详情页面包屑不能只绑定 `span onClick` 并在鼠标下看似可用；返回上级资源必须渲染为原生可聚焦按钮或链接，真实无障碍树中应出现可操作名称，并用键盘路径复验。
- 表格“首尾固定”不能只检查 CSS 声明。必须把内部容器真实滚动到最大 `scrollLeft`，比较首列左边界和尾列右边界在滚动前后保持不变，同时确认页面根节点没有横向溢出。
- 用户只反馈“页面打不开”时，先用根页面、主资源、业务深链和 API 组成快速失败检查，再看 Deployment、Endpoint 与前一容器日志；若入口直接拒绝连接且 Pod 因外部 MySQL CrashLoop，不能误判为 SPA 缓存或前端提交回归。
- Kubernetes 使用宿主机 Docker 容器提供外部 MySQL 时，依赖容器必须配置可恢复的 RestartPolicy；只把应用 Pod 验收到 Ready 不足以抵御 OrbStack/Docker 后续重启，应同时确认 MySQL `unless-stopped` 和应用重启后的 0 restart。
- 同一本地集群已有兼容的共享 GreptimeDB 时，不应再为 Pole 部署重复 standalone 实例；应通过 Pole namespace 内的稳定服务适配层复用共享物理集群，并用独立逻辑库隔离表、权限与查询边界。迁移收敛旧工作负载时必须保留原 PVC，直到历史数据确认导出或明确放弃。
- Handoff 是项目本地的会话协作资产，应写入仓库根目录 `.handoff/` 并通过 `.git/info/exclude` 排除；不得写到系统临时目录，也不得暂存、提交或推送。完成后必须同时用 `git check-ignore` 和包含全部未跟踪文件的 `git status` 验证排除生效。

## 2026-07-25：迁移主操作入口时必须删除旧入口

- 为解决操作不可见而把“编辑”等主操作移到内容区时，必须同步删除页首的同义入口；同一状态、同一权限、同一结果的按钮不能仅靠不同文案重复展示。
- 回归检查不能只断言新入口“存在”，还应断言同一状态转换的入口数量恰好为 `1`，并真实查看页面的完整首屏，避免局部组件验证漏掉跨区域重复操作。

## 2026-07-27：服务契约验收必须覆盖详情与协议原生语义

- 服务契约页面显示协议数量、接口行和原始文本，只能证明“列表可见”，不能证明“详情可用”；验收必须实际点击接口并验证详情可达、键盘可操作、方法重载可区分。
- Dubbo 不能只按通用 IDL 契约建模。设计与验收必须对照其原生 Metadata Center 体系，分别表达应用级服务发现、接口到应用映射、元数据修订、provider/consumer 服务参数和方法定义，再由适配层生成 Pole 的统一契约投影。

## 2026-07-28：配置模板能力必须嵌入配置资源任务层级

- 配置中心的主要用户路径应从配置分组进入具体 Namespace/环境，再管理配置项；不能因为新增模板领域对象，就把“配置模板”直接提升为与配置分组并列的默认主任务。
- 必须区分“可跨 Namespace 复用的模板定义”和“某个 `namespace + group + file` 下的模板配置文件”：前者可以是全局模板库，后者才是用户在配置分组上下文中创建、绑定和发布的配置资源。
- 模板模式应成为创建配置项时与普通文本并列的显式选择；Namespace Value、预览和 Template Release 切换应围绕该配置项展开，避免用户在无 Group 上下文的独立工作台与配置文件详情之间来回拼装流程。

## 2026-07-28：重试浏览器验收前必须重新读取实时权限

- macOS 的 Accessibility 与 Screen Recording 授权可能在两次操作之间发生变化；用户要求重试时，
  必须重新读取实时权限和窗口状态，不能沿用上一轮“未授权”的结论。
- 权限恢复后应继续完成真实登录、导航、页签与 Drawer 交互，并以最新 Kubernetes 静态资源为准；
  静态契约和构建结果不能替代此时已经可执行的像素级验收。
