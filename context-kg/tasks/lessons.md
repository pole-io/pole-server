# Lessons

- 当讨论 pole-control-plane 与 pole-console 的启动/部署标准化时，默认启动语义应是合并启动；参数只用于切换单独启动 `server` 或单独启动 `console`，不要把默认设计成只启动 control-plane 后再通过 `--console` 打开控制台。
- “合并启动”在 pole-control-plane / pole-console 场景里应优先理解为代码与运行时合并进 control-plane，而不是由 control-plane 再拉起一个 pole-console 外部子进程；除非用户明确要求双进程 runner，否则不要把子进程方案当成默认实现。
- 合并 console 后，默认产品入口端口优先给 console 使用 `8080`；如果 Apollo 协议端口与 console 冲突，应调整 Apollo 端口，不要挤占 console 默认入口。
- pole-control-plane 的默认启动模式必须按 `all` 理解和演示；`server`、`console` 只作为显式参数/配置指定的单独启动模式。
- 验证 console 页面数据时，必须验证 `8080` 页面运行时实际请求链路；后端 `8090` 接口返回数据只能证明服务端有数据，不能替代页面渲染验证。
- 对用户宣称 `8080` 可访问前，不能依赖 Codex 工具前台会话或普通 shell 后台子进程作为长期运行证明；需要确认服务脱离工具会话后仍由稳定进程管理，例如本机可用 `launchctl`，并再次验证端口、首页、静态资源和真实 API。
- 修复 console 鉴权问题时，不能只验证重新登录后的 curl；还要覆盖浏览器已有 `localStorage` token / `jwt` cookie 的旧登录态。后端代理不应在后端 401 前续期旧 JWT，前端遇到 HTTP 401 或 `401001` 应清理登录态并回登录页。
- 当用户评价页面设计时，先确认具体页面、抽屉、弹窗或空态；不要只优化主列表页，二级页面和无数据状态也必须按用户截图逐项处理。
- MCP tools 页面不应按普通后台表格处理；带有 input/output schema 的工具能力更接近 OpenAPI 文档，应优先设计为工具目录、参数/响应字段、示例和 raw schema 折叠的 API 浏览体验。
- MCP Server 注册语义应优先围绕 backend selector：关联 Pole 已注册服务时只要求 `backend_type=service` 和服务 `namespace/name`；只有自定义地址模式才要求用户提供 address，不要再把 `reference` 当成唯一后端表达。
- 排查 console 列表“接口有数据但页面为空”时，要优先核对标准响应解包：当前后端列表通常返回 `{data, amount, size}`，旧前端字段如 `services`、`namespaces` 只能作为兼容兜底，不能作为唯一数据源。
- 修复某一个列表页的响应字段错位后，必须横向扫描同目录其它列表页；不要只修用户指出的页面，同类字段如 `instances`、`users`、`userGroups`、`aliases`、`configFileGroups` 都可能同时落后于标准 `data/amount` 响应。
- 服务订阅页面展示的是服务关系，不应直接退化成三列表格；优先使用 caller -> callee 的关系流、节点和方向线表达，减少重复文字，让用户一眼看到谁订阅了当前服务。
- 服务详情、实例、订阅这类可直接访问的详情页不能依赖列表页写入的 Redux 临时态；刷新或直达页面时必须从 URL 参数恢复上下文并重新拉取数据。
- 服务详情页不应只使用裸 `Descriptions` 纵向堆字段；应先展示服务身份摘要和关键状态，再把基础信息、治理归属、可见性、标签、时间分组，空值用明确占位处理。
- 实例详情抽屉也不能使用裸 `Descriptions` 单列字段；应先展示 `host:port`、健康/隔离/健康检查等关键状态，再把运行信息、位置和标签分组，避免右侧抽屉显得像未设计的表单清单。
- 治理规则原型不能做成带大量解释性文案、PRD 入口和“为什么这样设计”的 AI 化页面；应对齐 TDesign 与现有服务/实例详情风格，默认只展示产品态信息：身份摘要、关键状态、基础信息、作用范围、规则定义、发布与订阅。
- 治理规则详情不能和当前治理规则实现差异过大；即便做抽屉或视觉优化，也应保留现有规则详情/编辑页的信息顺序：基础信息、目标服务、匹配条件、动作配置、发布记录，而不是迁移成另一套服务/实例详情信息架构。
- 治理规则详情的 demo/PRD 字段必须从真实 `github.com/pole-io/specification` proto 和现有前端 service 类型推导；不能把路由、限流、熔断、探测、无损上下线、泳道抽象成一套泛化字段后再展示，否则会和实际规则 spec 对不上。
- 治理规则详情的“对齐 spec”不能理解成在产品页直接展示 proto 字段名；spec 只用于保证数据结构和含义正确，页面呈现应优先复用当前 8080 治理规则详情/编辑页的分区、表单语言和用户可理解的字段文案。
- 治理规则列表页可以做统一工作台规范优化，但详情框应沿用当前 8080 治理页面的右侧详情面板和 `规则 / 版本 / 监听` 结构；不要把详情交互替换成新的抽屉模式，除非用户明确重新要求。
- 治理规则详情交互可以是抽屉，但抽屉内部的信息架构和视觉必须复用当前 8080 治理详情页；不要把“保持当前设计”误解为把抽屉改成常驻右侧详情面板。
- 元数据/标签编辑是跨服务、实例、命名空间、配置、认证等多处复用的核心控件，不应使用普通表格内联编辑；优先做成明确的键值编辑器，提供空态、重复 key 提示、直接新增/删除和紧凑扫描体验。
- 同一资源的查看态和编辑态必须使用同一套信息架构与分区命名；编辑态只应把只读值替换成控件，不能另起“运行配置/状态控制/元数据”等不同语言，造成同一抽屉前后风格割裂。
- 即便上游流程或 skill 模板给出英文提示，也必须转写为中文再发给用户；不要直接输出英文流程话术。
- 治理页面验证不能只看 8080 静态资源或 mock 页面；用户指出 8080 正常但接口仍报错时，必须用真实登录态或等价 JWT 走 8080 console 代理请求，并结合 runtime 日志和 MySQL schema 排查 5xx。
- 整理侧边栏时不能只验证当前模块和隐藏菜单结果；必须横向点击验证所有一级模块及其关键子菜单。TDesign Menu 的 `defaultExpanded` / `expandMutex` 组合不能在未验证点击交互时贸然改为只展开当前模块，否则可能造成隐藏子菜单仍占位并拦截点击。
- Console 侧边栏一级模块顺序应把 `AI 工具` 放在 `命名空间` 后面，再展示注册发现、治理、监控和认证；不要按普通后台末尾附加 AI 模块。
- 验证认证策略页面时必须同时覆盖自定义策略和默认策略；默认策略包含 spec 中更多系统资源类型，不能只用 `default=false` 或空列表证明策略查询正常。资源类型到 Console 响应字段的 map 下标调用前必须做存在性检查，避免新增资源类型导致 nil 函数调用。
- 注册发现列表页需要与 MCP 页面保持同一套控制台工作台风格：页头、指标栏、筛选工具栏和表格摘要列可以统一，但必须保留服务/别名 tab、服务详情跳转和原有操作链路，不要为注册发现另起一套视觉语言；网关应作为注册发现左侧菜单下的独立页面，不要合并进服务实例页内部 tab。
- 注册发现服务页优化不能只套 MCP 视觉骨架，还要检查实际截图里的区块间距：Tabs 内容区需要明确内边距，指标、工具栏、表格之间要有稳定 gap；表格首列不要重复展示已经有独立列的可见性信息，否则页面会显得拥挤且没有呼吸感。
- Console 侧边栏折叠态只应显示项目 logo 标记本身，不能换成其它插图或复杂图形；展开态使用完整品牌标识，折叠态使用同源 mini 标记，并保持固定尺寸居中。
- 治理规则详情抽屉既要沿用现有 `规则 / 版本 / 监听` 和编辑器分区，也要按抽屉产品形态重新处理标题区、正文留白和操作安全区；不要让 `StickyTool` 按页面级偏移漂浮到抽屉内容中间遮挡表格。
- 治理规则详情里的表单查看态不能像冻结的编辑表单；优先用 inspector 风格的弱边框分区、稳定间距和轻量表格表达规则定义，减少多层卡片阴影和 hover 浮起效果。
- 治理规则详情抽屉如果把 `StickyTool` 视觉改成标题栏按钮组，点击事件必须绑定到可见的图标+文字操作内容上，并用 8080 真实页面验证 `编辑 / 发布`；不要只改样式或只依赖 `StickyTool` 容器事件，否则文字/背景点击可能失效。
- 治理规则路由详情展示必须兼容新 spec 结构：真实数据可能在 `routing_config.caller/callee` 和 `rules[].arguments.arguments`，不能只读旧的 `rules[].sources[0].arguments`；验证时必须确认主调、被调、匹配 key/value、目标分组和实例标签都实际出现在 8080 页面。
- 治理规则详情字段修复不能只看某一类规则；路由、限流、熔断、主动探测、无损上下线、泳道都可能存在 spec JSON、DB JSON、API JSON 命名和前端读取字段不一致。修复时优先在 service 层做归一化，并用 8080 逐类打开抽屉验证关键字段是否真实展示。
- 治理规则详情抽屉的查看态不能沿用编辑态 `FormItem` 堆叠；当用户反馈对齐和滚动问题时，应优先把查看态改成紧凑 definition grid、关系摘要和固定列宽表格，编辑态再保留原控件，避免为只读展示付出表单布局的高度成本。
- 治理规则抽屉优化必须同时检查查看态和编辑态；TDesign `FormItem` 的固定 label width 与 controls margin 放进 CSS grid 后可能把内容区压到极窄，出现“暂无标签”逐字竖排。编辑态需要单独的控件友好 grid，并用真实 8080 点击 `编辑` 后验证。
- 治理规则编辑态表格不能只看表格整体是否溢出；还要检查单元格内交互控件是否互相覆盖。TDesign 横向 `InputNumber` 至少需要稳定列宽，否则会压到后续标签列；验证时要对关键控件做 DOM rect 对比，例如 `weightRight <= tagLeft`。
- 治理规则编辑器里子规则和实例分组有天然顺序语义时，不能只靠“添加/删除”维护列表；应提供折叠摘要和拖拽排序。拖拽只调整本地 `routing_config.rules` 或 `destinations` 数组，保存时再统一提交，避免拖动即触发后端写入。
- 治理规则中不同类型的多策略/子规则区块要保持一致的信息架构：路由子规则、限流子规则、熔断策略都应使用规则块 header 摘要、可折叠正文和表格化定义；不要让某一类退回 TDesign Collapse 或多层灰底卡片。
- 治理规则详情里同类规则块标题应统一为 `规则 [n]`，不要在限流等页面额外写成 `子规则 [n]`；分组标题下方避免放解释性长文案，优先把必要信息压缩到规则块 header 摘要中。
- 限流规则详情的规则块列表不需要外层 `子规则` 标题；内部 `规则 [n]` 已能承担结构识别，避免“子规则 / 规则 [1]”两层标题重复。
- 治理规则详情抽屉关闭时必须销毁或重置内部编辑器状态；用户未保存直接关闭后，重新打开同一规则应回到查看态，不能沿用上一次的 `editorState.editable=true`。
- 治理规则发布页不能沿用页面级长表单；应按抽屉产品形态展示规则身份、版本信息、发布策略和灰度条件，灰度条件用表格化条件行保证对齐，并保留原 `MatcheLabel[]` 提交结构。
- 治理规则发布页的策略选择不能只放普通 radio；发布范围应通过可点击策略卡和轻量流向图表达，全量/灰度的生效对象要一眼可见。抽屉 footer 也不能让按钮散落，应固定为当前策略摘要加右侧主次操作。
- 治理规则详情查看态必须全链路只读；不能只隐藏保存按钮，所有 `InputNumber`、`Switch`、`Textarea`、表格编辑器和弹窗入口都要受 `editorState.editable` 控制。查看态优先渲染文本、Tag 或只读代码块，编辑态再渲染输入控件。
- 治理规则查看态横向排查不能只看用户截图中的那一类规则；无损上线这类使用 `readonly/borderless/disabled` 保留 `InputNumber` 或 `Switch` 外壳的实现也会让用户觉得可改，查看态应优先渲染纯文本或 Tag，编辑态再渲染控件。
- 治理规则 MySQL 模型收敛按方案 A 理解：`governance_rule/governance_rule_release` 覆盖所有治理规则类型，包括泳道；泳道以 lane group 为聚合根，lane rule 是 group JSON 内的子对象，不再默认保留 `lane_group/lane_rule/lane_group_release` 专用表。若用户明确说不考虑数据迁移，实现方案不需要为旧分表数据做自动迁移。
- 统一治理规则表后，cache 也要统一更新源：由 `GovernanceRuleUpdateCache` 轮询统一表并按 `rule_type` fan-out 给各类型 watcher；不要让路由、限流、熔断、探测、无损、泳道 cache 各自再查一次 DB。
- 完成数据库模型收敛后，必须同步清理三类残留：SQL 初始化脚本、测试/运维清理 SQL、以及本地真实数据库中的旧表；不能只改 store 实现就认为收敛完成。真实库删表前要先确认旧表为空或明确迁移策略。
- 判断历史表名是否仍有效时，必须同时核对 SQL DDL、真实库 `information_schema`、store 实现和测试套件直接 SQL；不能因为某个历史注释或测试残留就把它误判为仍需保留的独立表。
- 长期技术方案和架构/领域知识必须归档到 `context-kg` 并遵循其 schema、index、log 规则；不要在 `docs/design` 下新增孤立方案文档。`context-kg/tasks` 仅用于计划、进度、review 和 lessons。
- 调整 `context-kg` 时不能只移动文档内容，还必须同步设计和更新知识库 taxonomy：业务知识放 `business/`，技术方案和 ADR 放 `technical/adr/`，模块/接口/环境/约定放 `technical/` 对应子目录，测试/缺陷/自动化知识放 `quality/`；同时更新 `_meta/schema.md`、`_meta/index.md`、`_meta/log.md` 和仓库级 AGENTS/CLAUDE 规则。
- 设计 pole-control-plane 的 A2A 能力时必须严格限定为 A2A Agent Registry：Agent Card 注册、发现、索引、治理元数据和管理 API。A2A task proxy、SSE streaming 转发、push notification broker、task 状态机和 artifact 存储属于数据面/网关/agent runtime，不应写成 pole-control-plane 的二期能力。
- 实现 A2A Agent Registry 时不能只落后端注册表；Console 页面、列表筛选、抽屉新建/编辑、Agent Card 查看和技能详情都属于功能完整性的一部分，需要和 MCP 页面保持同一套控制台交互语言。
